# TBR-05 负载与证据工具

协议源：[正式负载测量协议 v1.0](../../../../docs/10_验收证据/19_后端综合验收/01_正式负载测量协议_v1.0.md)。这些工具由此前本地部署缓存中的正式负载脚本纳入版本管理；纳入不代表当前源码已经完成云端验收。

| 文件 | 用途 |
| --- | --- |
| `01_seed_formal_data.py` | 向空的 `t22_perf_` 隔离库写固定种子夹具，凭据输出到仓库外 |
| `02_formal_service.py` | 启动独立 Waitress 实例，可选应用/SQL/排队计时 |
| `03_tbr05_load.py` | 真实会话、完整响应体计时、请求与资源 JSONL；默认360并发、300秒预热、600秒正式窗口。HTTP区间在完整体接收后结束，连接关闭和后处理另留阶段时间；CSV核验由有界队列另行处理，不把核验时间计入在途 |
| `04_sample_windows_resources.ps1` | 应用服务器 Windows CPU、进程与磁盘采样 |
| `05_align_resource_evidence.py` | 按 UTC 分钟对齐请求与服务器资源，只用于关联分析 |
| `07_tbr05_sharded_load.py` | 多进程发压入口，总线程数由各进程均分，共享同机单调时钟与UTC起点 |
| `shard_evidence.py` | 校验分片身份、窗口与逐进程采样，合并原始区间与采样 |
| `06_evaluate_tbr05.py` | 从原始请求重算分项P95、逐分钟吞吐、失败、导出完整性及在途采样门槛 |

运行负载端需要 `requests`、`psutil`，服务端另需后端锁定依赖及 Waitress。每轮登记实际版本、源码提交与工具哈希。不要向仓库提交账号文件、原始请求、运行配置或日志。

云端负载只在正式复测窗口执行；正式命令固定 `--concurrency 360 --warmup-seconds 300 --formal-seconds 600`，不设置 `--only-group`。应用池测试用重复 `--target-base` 指向各个应用内网端口；`--base` 仅作单端口诊断的后备地址。正式前完成独立库、迁移、夹具计数、进程/连接预算与资源采样预检。默认参数只是候选窗口标签，不能当成通过结论。

在应用服务器的 `backend` 目录中，Waitress 候选进程由 `backend/运行脚本/02_正式负载应用池.ps1` 管理。启动前在管理员 PowerShell 设置 `T22_FORMAL_LOAD=1`、隔离库配置路径、Python 路径及包含当前内网地址的 `T22_ALLOWED_HOSTS`，再显式传入 `-BindAddress`；脚本会校验隔离库名、8×48 连接预算、候选配置和端口，并在 `C:\ProgramData\T22\formal-load` 保存进程状态与日志。启动命令为 `.\运行脚本\02_正式负载应用池.ps1 -Action start -BindAddress <当前应用机内网IPv4>`，停止命令为 `.\运行脚本\02_正式负载应用池.ps1 -Action stop`。不要照抄旧候选中的内网地址；状态和日志不进仓库。

发送端对病历更正和采纳响应立即更新版本引用；导出与其他响应由八个核验线程复核完整字节、CSV行数与摘要。有界队列若积压，会阻塞发起线程并使实际HTTP在途下降，必须视为客户端容量问题，不能用登录账号数或核验排队数补足360在途。

判定命令：`python 06_evaluate_tbr05.py --summary <prefix.summary.json> --requests <prefix.requests.jsonl> --inflight <prefix.inflight.jsonl> --output <仓库外新报告.json>`。报告并列给出0.5秒在途采样与完整请求区间重建的并发最值；两种证据都必须覆盖全窗且恰为360，否则自动判定失败。退出0只表示自动检查项满足；完整验收还需人工复核环境、数据、固定混合比例、资源/错误日志、完整范围导出与峰值内存。大小分层报告分位，不擅自追加协议未明确冻结的分层P95硬门槛。

应用池有8个独立端口；发压时每个端口都必须作为一个目标传入，不能只用 `--base`，否则其他进程收不到负载。Linux发送机可用 `args=(); for port in $(seq 18930 18937); do args+=(--target-base "http://${APP_IP}:${port}"); done` 生成参数，再将 `"${args[@]}"` 传给 `03_tbr05_load.py`。360个发压线程会按工作线程编号均分到目标，摘要记录目标数和每个目标分配的线程数；旧 `--tunnel-base` 仍可使用。本候选为8进程×48线程、MySQL上限512，以360并发下每端口45个客户端为起点，最终须由队列/CPU/DB实测确认，不视为已验收。

本地工具验证：`python -m unittest discover -s backend/tests/performance/tbr05 -p "test_*.py" -v`。该命令使用合成证据，不连接数据库或云服务器。

标准造数脚本同时生成106,640条明确标注为演示的建议（6,665条采纳通道病历，每条16个独立目标），清单记录总量及每店数量。发压前核对清单容量；旧的无建议清单必须重新生成，不再使用临时补数脚本。采纳只消费预分配目标，每个建议一次；达到容量上限会明确失败。该改动不改变七类请求比例、病历数量及导出范围分布。


## 多进程发送候选

单进程核验背压已在R14证据中复现。多进程入口默认4个独立进程，总计仍360线程（每进程90），使用同一固定夹具和原业务比例/范围。先按60秒预热+120秒测量诊断，再按300+600正式窗口执行；短测不是验收。

```bash
args=()
for port in $(seq 18930 18945); do args+=(--target-base "http://${APP_IP}:${port}"); done
python 07_tbr05_sharded_load.py --private-accounts "$ACCOUNTS" --output-prefix "$PREFIX" \
  --processes 4 --concurrency 360 --warmup-seconds 60 --formal-seconds 120 \
  --gil-switch-interval-ms 0.1 --capture-gc-pauses "${args[@]}"
```

账号与无后缀输出前缀均在仓库外，且不得复用已有前缀。控制器提前45秒生成共同起点；子进程认证若错过起点则失败，不缩短预热。任一子进程失败或超时，控制器终止其余子进程并保留退出状态；缺失或不一致证据不会生成成功摘要。

各进程内部仍保持原20项混合周期；请求号区间分离，工作线程号全局唯一，端口分配按全局线程号计算。更正/校验病历目标按进程固定分区，采纳的全部16个建议槽跟随同一病历归属，防止版本缓存跨进程失效或重复采纳。单进程入口默认行为保留。

各分片的原始请求、采样、GC、摘要及标准输出分别保留。父摘要只在检查共同起点、源码、夹具、配置、完整窗口和线程归属后生成。合并请求保留原始浮点起止值；合并采样为各进程最近一次真实采样的异步求和，包含分量时间，不把它当作精确区间并发证明。各分片必须单独满足采样覆盖要求。最终仍由原验收器检查完整请求区间、每次5ms交接以及累计和连续1秒限制。

客户端资源采样包含控制器和全部发压子进程；GC事件通过shard_index区分进程，分析时必须按(进程,代数)配对。打包脚本需收集父前缀及其`-shard-`子前缀，不能只收集父前缀加点号的文件。正式900秒负载前须把应用池/采集/发送单元的运行期限同步放宽到足以覆盖共同起点等待、预热、测量和证据收尾；不得沿用短测的12分钟应用池上限。


### 服务端线程切换候选（默认关闭）

`02_formal_service.py`新增可选`--gil-switch-interval-ms`，也可通过`T22_SERVER_GIL_SWITCH_INTERVAL_MS`传入，显式命令行优先。不提供时保留解释器默认设置。仅作用于该服务进程的运行期，退出或异常时还原，启动日志记录实际`GIL_SWITCH_INTERVAL_MS`。值须为有限正数；例如0.1代表0.1毫秒，不是280毫秒响应门槛，也不保证实际调度间隔。

后续先以同源码、同数据及同配置分别比较默认值和0.1ms候选，记录全部进程生效日志、CPU、SQL墙钟等待、真实完整响应及发送端交接，不在测量窗口中调整。该候选尚无服务端云端收益证据，不因此变更持续在途或响应判定。当前正在运行的活跃会话复验不部署此改动。


2026-11-06 R17/R18同源码对照已完成：服务端0.1ms使七类时延明显恶化、吞吐大幅下降，因此不采用；后续保持默认值。详细原始证据索引和采样局限见实施计划33的R17/R18节。此前“尚无服务端云端收益证据”不应理解为等待采用；现有证据是该候选负收益。


### 精确统计与流式证据合并

工作进程将完整请求记录交给原落盘队列，汇总仅保存64位数值数组、计数和范围/剖析分类；不常驻请求字典，不抽样或舍弃失败/慢请求。控制器逐条验证请求ID、线程归属和原始区间后写入合并文件，最后才生成成功摘要。仍保留完整请求ID去重集合；数组及ID集合随请求数增长，并非常数内存。采样缺失、后续重复ID或缺失线程仍使控制器失败，已写的部分输出不得当作成功证据。

离线78项回归通过；R17八个分片共178317条回放生成的合并请求SHA与旧文件逐字节一致，全部旧汇总字段相等。本地4进程/8线程HTTP联调8172次、七类均覆盖且零核验失败；仅验证工具管线。1万条实际记录的合并+汇总Python分配峰值由48.38MB降至1.55MB；100万条合成统计约32.26MB，不代表真实HTTP/CSV队列或云端峰值。新工具尚须云端验证实际RSS、交接、采样和完整900秒容量。


### Windows CPU归因采样

保留原processes应用/数据库字段，增加all_process_cpu：逐进程PID、启动UTC、总/用户态/内核态累计CPU秒；不采集命令行。排除Idle PID0，按PID和启动时间匹配相邻样本后求差，不能把累计CPU秒当瞬时百分比；受保护或退出进程无法读取时保留空值和sampling_error，不按零消耗处理。全机新增用户态/内核态百分比，与已有总CPU分别保留原始计数器值，不强制相加一致。

每行保留PDH原timestamp_utc，并另记sampling_started/completed_utc、sampling_duration_ms及process_snapshot_started/completed_utc。进程快照在PDH之后读取，并非完全同步；采样耗时包含Get-Counter等待，不能当作采集CPU开销。现有两样本读取在本机约2秒一行，配置1秒不保证1秒实际间隔。

本地Windows 10秒原生运行写出5行、每行约426进程，无整行采样错误；非管理员下183个进程不可读并显式标记。79项工具回归通过，新增用例覆盖其他服务CPU、用户/内核拆分、启动身份、Idle排除和不可读记录。该验证不能代替云端管理员权限及高负载采样验证。
