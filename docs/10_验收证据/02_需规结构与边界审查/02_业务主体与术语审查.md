## 2. 建议采用的主体与术语区分

以下为对既定范围的清晰表达建议；没有增加运行角色，也没有确认尚待评审的字段细则。

| 术语 | 在产品正文中的含义 | 不应混为一谈的对象 |
| --- | --- | --- |
| 医生账号 | 以医生角色登录、代表一名医生操作系统的身份；读写范围由所属门店和接诊归属约束 | 宠物、宠物主人、学生本人、开发代理 |
| 前台账号 | 以接待角色登录，操作该账号在所属门店本次接待的接诊信息 | 医生病历全文、曾接待宠物的全部历史 |
| 管理账号 | 以管理角色登录，按已确认范围查看本店汇总、脱敏审计并审批规则和模板 | 无边界的超级管理员、教师或项目负责人 |
| 宠物 | 门诊诊疗对象，病历内容描述的对象 | 操作账号、访问权限持有人 |
| 宠物主人 | 业务相关方和主诉等信息的可能来源；本范围不提供主人登录端 | 因拥有宠物而自动获得系统角色或全文读取权限 |
| 接待建档 | 前台建立一次到院接诊登记 | 医生已经完成诊疗、处方或AI采纳 |
| 接诊归属 | 一次接诊关联的门店、接待前台账号、接诊医生账号 | 数据财产权、病历属于医生本人身体状况 |
| 宠物病历 | 与一次接诊关联的诊疗记录，由有权医生账号操作 | 前台接诊信息投影、管理统计、其他就诊的历史全文 |
| AI 建议 | 等待人决定采纳或不采纳的建议内容 | 已经成为正式病历的事实、具有业务审批权的账号 |
| 系统业务审批 | 在运行系统中由有权管理账号对规则/模板版本进行的审批记录 | 学生对需求设计的真实评审、教师给分 |
| 开发者/教师/主代理/子代理 | 项目开发与评审参与者，记录于过程材料 | VetRules 新增的第四、第五类运行角色 |

“账号”用于说明可认证和授权的操作主体，不要求本轮固定用户表、账号编码或认证框架。运行时 AI 是否外部调用仍待方案决定，不能因术语表提到 AI 就默认新增一个有病历读取权的登录账号。

## 3. 可直接采用的措辞替换建议

以下替换旨在澄清主体；凡涉及未确认字段或流程，仍应标注提案或待定。

| 原有简写 | 建议替换 |
| --- | --- |
| 医生仅能读写本人接诊病历 | 系统仅允许当前登录医生账号读写其在所属门店负责接诊的宠物病历。对其他医生负责或其他门店的病历读取请求，系统应拒绝并记录请求者、目标记录及拒绝原因 |
| 前台仅看本人本次接诊基本信息 | 系统仅允许当前登录前台账号读写其在所属门店本次接待所形成的接诊信息；可见字段按接诊字段定义执行，不包含诊断、处方、AI建议原文及病历全文 |
| 医生处理本人病历的告警 | 系统应允许当前登录医生账号处理与其负责接诊的宠物病历关联的告警；不得因处理告警而开放其他医生或其他门店的病历内容 |
| 管理查看本店汇总 | 系统应向当前登录管理账号提供其所属门店的汇总统计；统计输出不包含诊断、处方、AI建议原文或病历全文，具体指标清单另行确认 |
| 主人是用户 | 宠物主人是业务相关方和信息来源；本系统仅提供前台、医生、管理三类操作账号，不提供宠物主人登录端 |
| AI经采纳后入病历 | 系统应在AI建议进入对应宠物病历前核验采纳人及采纳理由，并保留建议与该病历的关联；不采纳的建议也应登记留存。采纳界面与字段细则仍需设计和评审 |
| 人机审查由本人及代理完成 | 从产品需求正文移至项目协作记录；产品 FR-03 另写为“系统应逐项保存人机分工登记及实际执行情况，并在不一致时提示复核” |

前两行不应只改角色表而保留正文/用例中的“本人病历”。应同步检查角色表、权限规则、用例参与者、数据字典、告警与审计对象的指代。任务书原文作为来源可保留原句，解释句应给出清晰主体。

## 4. 用例可读性与边界缺口

下表是完善既有 FR 的用例输入，不是已批准的新业务流程；没有具体批准人的条目仍保留待定。

| 对应功能 | 业务读者需要读懂的最小场景 | 目前需补清的边界 |
| --- | --- | --- |
| 接待与 FR-05 | 前台账号建立本次接诊信息，关联一只宠物和接诊医生；系统形成可信归属 | “接诊建档成功”的可观察结果、必填资料和同店医生选择仍需给提案；不能自动采纳本文术语表为字段清单 |
| FR-05 医生读取 | 医生账号选定其负责接诊的一只宠物的本次病历，系统核验范围后返回允许内容并审计 | 接诊信息如何供对应医生使用，应列字段与关联边界；既不把前台字段永远封死给医生，也不推导为跨角色任意共享 |
| FR-05 拒绝 | 当前账号请求同店其他医生负责的宠物病历或跨店病历，系统不给正文并记录拒绝 | 明确失败输出不能夹带主诉、诊断等正文；同一宠物编号不能使历史病历自动可见 |
| FR-01/02 审批与版本 | 有权账号提交候选规则/模板，管理账号审核该候选，系统在满足生效条件后提供相应版本 | 谁能提交、驳回后状态、生效触发与历史版本解释待提案；审批预览不能为了“看效果”向管理开放真实病历全文 |
| FR-03 分工登记 | 有权操作账号登记工作项、计划人机分工及实际执行情况；系统对不一致给出可见复核提示 | 工作项覆盖范围、维护/复核账号、实际执行记录如何进入系统仍待明确；项目代理分工表不能充当此产品功能已经实现的证据 |
| FR-04 追加更正 | 接诊医生账号针对其负责的宠物病历追加处方、用药或剂量更正，系统保留原项及关联、操作者、时间与理由 | 用户看到的是“追加更正”而非可覆盖原记录的“编辑”；不延伸到其他医生的记录 |
| FR-06 采纳/未采纳 | 医生在有权病历中查看带来源的AI建议，作采纳或不采纳登记；采纳满足条件才进入对应病历 | 未采纳是正常分支而不是失败；采纳人身份如何可信记录和建议来源仍待方案明确，不能由任意客户端伪填 |
| FR-07 告警 | 医生在其有权范围看到未处理告警，提交处理结果，系统保留处理记录 | “后台持续提示”不等于只有管理看告警；命中字段名与敏感值的展示需分开；系统类告警的责任不能在本轮擅自补定 |
| FR-08 导出/审计 | 账号给出允许范围和导出用途，系统按授权生成结果并登记；管理在本店脱敏审计内按病历标识或操作者检索 | 各角色允许导出什么、一次导出的范围和审计可见字段需明确；能查询病历标识不等于能读取病历正文 |

用例中的“有权账号”是尚待补齐的角色条件占位，不能成为最终需求的万能主语。修订稿应将已知角色写实，把未知角色/字段列入未决项，避免读者以为系统会自行判断审批者。

### 8.2 最多四项易懂的边界风险

1. **“宠物信息相同”不等于“每次记录一起改”。** 若前台更改共享宠物资料便改掉其他前台/医生历史内容，会越出按次隔离；建议字段按本次接诊的可见内容解释，历史更新语义另列设计，不能默认联动。
2. **医生关联读取不等于所有角色互通。** 医生只读其负责接诊所需的上述接诊投影，不能借关联取回其他医生病历、同宠物全部历史，也不因此取得前台资料写权。
3. **“脱敏”不能只删宠物名字。** 主诉、诊断、告警命中值、导出用途自由文本仍可能包含正文；管理展示采用明确元数据清单。本店统计和审计仍须定义计数口径、事件所属门店，避免通过筛选或审计链接进入临床正文。
4. **查看、必填和导出是三种不同决定。** 本次表只提字段与查看/录入范围；既有方向批准不能覆盖所有新增必填项，页面可见也不能自动推成可导出。导出继续等待主代理单独确认的角色与字段边界。

### 10.2 错绑宠物的纠错方式【P，必须一并审清】

仅写“不能改宠物编号，重建一次接诊”仍不闭合：原错误记录会继续像正常接诊一样可被使用。建议采用一个**仅用于错误建档的标记及重建关联**，不扩展为通用取消、退款、转诊或换班流程：

1. **尚无诊疗内容**：原接待前台在原有范围内登记“错误建档”及理由；系统保留原编号、原宠物关联和历史，将其明确标记为不再用于正常诊疗，再以正确信息建立新接诊并保留两者纠错关联。新接诊仍按原有建档权限独立验证，不能自动接管他人记录。
2. **已经有诊疗内容**：前台只能登记建档错误说明，不能删除、改绑或使临床记录自行消失；由负责该病历的原接诊医生追加纠错说明并确认停止在错误接诊中继续新增诊疗，再按正确对象重建。此处的医生确认是P新增边界，不冒称此前C-06已批准；不额外引入管理全文权限或第四角色。
3. 两种情况都保留旧病历/处方、既有告警、审计和错误标记；原有未处理告警不因登记错误被自动关闭。历史读取和导出仍按原权限并带错误标记，纠错关联本身不授予另一接诊的全文访问权；不得静默复制旧诊疗、处方或AI采纳内容到新宠物。

这里的“停用”只是阻止旧误建接诊被当作正常入口继续新增诊疗，**不是删除历史、追溯取消已有处方或把旧记录移给新宠物**。实施前需由真人明确接受该窄范围状态含义和操作主体；若不接受，不能一边保留“禁止改绑”，一边不说明错误记录如何处置。

统计口径建议同样保持最小【P】：接诊数按实际成功建档事件计数，错误标记不静默删除原事件；新建正确记录另计。无需本轮新增统计指标，但说明该数是建档数，不冒充实际有效诊疗次数。若希望排除错误建档，应作为另一明确口径决定，不由实现自行扣减。
