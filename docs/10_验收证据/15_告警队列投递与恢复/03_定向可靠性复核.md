## 发现：1项中风险，无高风险发现

### R1 / 中：连接存活而发布确认缺失时，默认worker可无限停在单条发布

位置：`clinic/delivery.py:111–113`（阻塞发布确认），`:42–45`（连接参数），`:208–219`（整批发布后才消费）；`management/commands/alert_delivery.py:30–43`（外层轮询需等待整轮返回）。

触发条件：AMQP连接建立成功，消息已发送；broker或中间链路迟迟不返回该条Basic.Ack/Basic.Nack，仍转发心跳，也未发送Connection.Blocked/Close。可以用AMQP代理仅过滤发布确认、继续转发其他帧复现。broker在持久化/复制确认迟滞时也可能保持连接存活；此处不声称本次复核制造过真实broker故障。

当前结果：`basic_publish`没有应用层截止时间，`finally: close(...)`、`finish_claim`及外层sleep/下一轮均不能到达。默认 `--phase both` 同一线程先发布后消费，因此已有队列中的事件也不会由该worker继续落收据，后续outbox同样停等。30秒租约到期能让另一个worker接手，但不会唤醒已经阻塞的worker；单worker运行须外部重启才能解除该次等待。此项影响处理活性，不会把确认误写为收据或破坏业务幂等。

现有参数不能提供该截止：本机Pika 1.4.4源码 `connection.py` 对socket_timeout、stack_timeout的定义是TCP连接/协议栈建立时限；blocked_connection_timeout在 `_on_connection_blocked` 收到显式通知后才启动；heartbeat只判断连接活性。`BlockingChannel.basic_publish`调用 `_flush_output(self._message_confirmation_result.is_ready)`，其完成条件是确认就绪或通道/连接关闭，没有发布操作计时器。

最小离线复现：在现有依赖环境调用真实Pika `basic_publish`和真实两层 `_flush_output`，只将底层IO换为始终存活、缓冲已清空、不交付确认的替身；第10001次poll由复现工具主动中止，避免留下挂起进程。代码无需Django设置、数据库或网络：

```python
from unittest.mock import MagicMock
from pika.adapters.blocking_connection import (
    BlockingConnection, BlockingChannel, _CallbackResult,
)

class HarnessStop(Exception):
    pass

polls = 0
def poll():
    global polls
    polls += 1
    if polls == 10001:
        raise HarnessStop()

conn = BlockingConnection.__new__(BlockingConnection)
conn._impl = MagicMock()
conn._impl.is_closed = False
conn._impl._get_write_buffer_size.return_value = 0
conn._impl.ioloop.poll.side_effect = poll
conn._closed_result = _CallbackResult()
channel = BlockingChannel.__new__(BlockingChannel)
channel._impl = MagicMock()
channel._impl.is_closed = False
channel._connection = conn
channel._delivery_confirmation = True
channel._message_confirmation_result = _CallbackResult()
try:
    channel.basic_publish('', 't22.app.review.offline', b'{}', mandatory=True)
except HarnessStop:
    print({
        'real_pika_basic_publish_returned': False,
        'io_polls_without_ack': polls,
        'scheduled_deadline_count': conn._impl.ioloop.call_later.call_count,
    })
```

本次实际输出：

```text
{'real_pika_basic_publish_returned': False, 'io_polls_without_ack': 10001, 'scheduled_deadline_count': 0}
```

该复现证明实际依赖的等待条件无发布截止，不是墙钟性能测量，也不代替端到端故障实验。应用调用点未添加额外timer，故会继承此等待行为。

最小修复方向：给发布阶段增加明确的操作截止（也覆盖建立通道、声明、启用确认等阻塞RPC），到期中止该连接的等待并将“可能已发出”的尝试按uncertain保留同一event_ref；继续使用现有租约围栏，避免用无限等待的优雅close抵消该截止。补一项受控代理测试：丢发布确认但保持心跳/连接，不主动断连；断言worker在限定时间返回恢复状态，后续轮次或消费可以推进，同一事件重投不新增Hit/Alert。

现有 `test_real_broker_confirm_dropped_by_proxy_is_not_claimed_delivered` 使用 `ConfirmLossProxy`，代理发现真实Basic.Ack后立即断开两端，验证了断线恢复；它未覆盖“缺确认但连接持续存活”的条件。

## 其余重点的复核结论

- 旧租约结果写入outbox前持行锁并核当前token及到期时间；收据优先将事件保持delivered。旧attempt补记自身结果未覆盖新持有者的outbox状态，未发现实质围栏缺陷。
- published与delivered分离；前者留下一次核对时间，后者必须来自持久收据。重复消息在同一outbox行锁下复用一对一收据，只递增传输计数，不新增Hit/Alert或改医生处理结果。
- 正常消息收据及delivered在同一atomic内完成，退出事务后才basic_ack；DB异常不ack，连接关闭后允许重投。发布落库失败保留租约，等待到期恢复。这些路径已有对应状态测试及主代理真实MQ测试，未发现新的高/中风险实质问题。
- 无效消息按标准原因和SHA256摘要记拒绝，不保存正文；消息只有两个UUID，CLI仅输出传输元数据或标准错误码。指定代码范围未发现临床正文/凭据直接进入消息、拒绝表或显式CLI错误输出。
- 迁移新增唯一收据和outbox状态约束与模型匹配。未将本批无新增Web端点、无页面或R-ALERT字段不扩展判为缺陷。

除R1外，本范围没有识别到可复现的高/中风险实质问题。本结论仅覆盖所列代码与离线等待条件复现；修复后应补相应测试，再由主代理完成本批回归及真实停复证据。
