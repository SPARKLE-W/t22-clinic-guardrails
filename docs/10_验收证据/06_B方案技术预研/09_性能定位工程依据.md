# 性能定位工程依据：Waitress排队、单机进程与连接预算

> 2026-10-21，AI工程研究记录。已读局部AGENTS、设计目录07、本阶段05/07；以已安装Waitress3.0.2源码及官方资料为依据。只读研究与一次MySQL变量/状态查询，未改实验代码、配置或其他报告，未启停服务、安装组件或运行负载。以下为可执行候选，不是性能达标结论或最终架构批准。

## 1. 本轮结论

1. Waitress队列在WSGI应用之前；仅有Django/app、SQL及commit计时，不能直接得到该队列等待。应将dispatcher入队至worker开始服务单独关联到每次请求。
2. 已安装版本以固定线程池处理任务，没有内置多worker进程选项；多`listen`地址也不等于多进程。最低成本诊断可用两个独立进程、两个回环端口；统一入口再候选评估一个Windows可执行反向代理。
3. 当前MySQL实际`max_connections=151`。先比较`1进程×32线程`与`2进程×16线程`，同时固定总客户端数和分布；不能同时增加服务进程、总线程和发压进程后把收益归于单一因素。
4. 客户端两个180线程进程必须拥有不同的全局worker编号和目标记录。直接启动两份当前180线程脚本会重复选中index0—179的记录，制造版本竞争。

这些建议承接[设计07的性能定位出口](../../04_%E8%AE%BE%E8%AE%A1%E4%B8%8E%E6%8E%A7%E5%88%B6%E6%96%87%E4%BB%B6/07_B%E6%96%B9%E6%A1%88%E6%80%A7%E8%83%BD%E6%94%B6%E5%8F%A3%E4%B8%8E%E5%AE%9E%E7%8E%B0%E5%89%8D%E7%BD%AE%E4%BB%BB%E5%8A%A1.md)、[05的实测限制](05_%E7%AB%AF%E5%88%B0%E7%AB%AF%E8%B4%9F%E8%BD%BD%E7%BB%93%E6%9E%9C.md)与[07的开放风险](07_%E9%A2%84%E7%A0%94%E7%BB%BC%E5%90%88%E7%BB%93%E8%AE%BA%E4%B8%8E%E5%90%8E%E7%BB%AD%E4%BB%BB%E5%8A%A1.md)，不改变题定指标或授权/审计要求。

## 3. 排队究竟在哪里，怎样观测

本地真实路径为：`HTTPChannel`收齐请求体 → `server.add_task(channel)` → `ThreadedTaskDispatcher.queue.append` → worker `popleft` → `channel.service()` → 构造`WSGITask`并执行WSGI应用。连接继续有已缓存请求时，会在前一次服务结束后重新调度。依据：[channel入队](C:/Users/29512/.cache/t22-runtime/venv/Lib/site-packages/waitress/channel.py:224)、[dispatcher入队](C:/Users/29512/.cache/t22-runtime/venv/Lib/site-packages/waitress/task.py:106)、[出队服务](C:/Users/29512/.cache/t22-runtime/venv/Lib/site-packages/waitress/task.py:64)。

最小观测可分两层，先保留同一版本和原业务行为：

| 观测 | 最小接入建议 | 能解释什么 |
| --- | --- | --- |
| 队列及忙线程趋势 | 低频读取dispatcher在其锁保护下的queue长度、线程数、active_count，保留Waitress队列警告；在锁外写观测日志 | 是否出现积压及其时间范围；不能产生每请求排队P95 |
| 每次派发等待 | 在实验入口用诊断dispatcher包装每次入队对象；持原锁、append前记录单调时钟，worker调用包装对象的`service()`时记录开始，再委托原channel；`cancel()`也必须委托，保留原警告/唤醒语义 | `service_begin-enqueue`为本次dispatcher等待及调度时间，可按请求关联统计；无需复制整个worker循环或改site-packages |

`create_server(...,_dispatcher=...)`本地确有传入点，但源码标为test shim，是**内部诊断接入**；自供dispatcher还须按设定显式建线程池，不能只设server的threads就假定已生效。应锁定3.0.2，核对包装前后状态码、响应体、失败样本及幂等效果；不是承诺稳定的正式监控API。入队时间若只记在调用`super().add_task`之前，则还含等待dispatcher锁的时间，须据此命名，不能称纯deque等待。

每次入队应有独立观测对象，不能在会复用的channel上只放一个时间戳后任其覆盖。关联使用随机请求观测ID、路径类别、进程ID及必要时序，不落临床正文、认证信息、SQL参数或cookie。队列单位在本版是待调度的channel服务项；有HTTP流水请求时，尚在channel内等前序请求的时间与dispatcher排队不同，应分开说明。

原警告深度为`len(queue)-idle_threads`，触发条件为queue长度大于可用空闲线程数；它不是连接总数，也不是毫秒数。不能把警告里的depth直接当请求等待时延。

建议关联时序：`enqueue → service_begin → wsgi_begin → wsgi_iter_end`，再关联SQL总时长、显式commit及客户端完整响应接收。WSGI开始到迭代结束也不等于客户端收齐字节，Waitress仍有输出缓冲/主循环发送。端到端减去app耗时所得残差还包含接收、网络/调度与客户端读取，不能全部命名为服务端排队；各分项P95也不能相加当端到端P95。先按同一次请求核对各时间，再分别统计分布。

| 候选 | 本轮可执行的下一步 | 对照边界 |
| --- | --- | --- |
| M0：两个Waitress进程、两个回环端口，客户端固定均匀分片直连 | 复用同一WSGI应用和配置，候选端口18723/18724先查空闲；先比较1×32与2×16。每端口应覆盖五类、五店，核实际监听PID及线程数 | 无新代理依赖，适合辨认进程因素；没有测试统一入口，不能直接作最终部署成绩 |

Waitress多`listen`共用同一dispatcher，并不会额外产生Python工作进程；不能把它当M0。也不采用多个Windows进程凭`SO_REUSEADDR`争同端口来冒充已验证负载均衡。候选均是同机分层单体的不同运行入口，未引入跨机集群。

M1初次对照保持代理重试关闭、无响应缓存，记录代理转发失败；不要用自动重发掩盖失败。真实session/CSRF、授权、必要审计、OperationResult和策略状态继续走同一数据库，使用一致配置；应用进程不能依赖本地内存实现全局幂等/授权正确性。最低跨进程核对为：登录后通过两个上游读取同一合法范围，同键写入落到不同进程仍只发生一次效果；不得因扩进程删去这些机制。Waitress本地环境固定写`wsgi.multiprocess=False`，不应把该值当成外部绝无其他应用实例的保证。

## 5. MySQL实际配置与预算

本轮配置文件[mysql.ini](C:/Users/29512/.cache/t22-runtime/mysql.ini)没有显式`max_connections`。执行`mysqld --defaults-file=... --verbose --help`只读帮助显示151（没有启动daemon）；父代理已运行的13322实例另经专用账号只读查询：

| 本次返回字段 | 值 |
| --- | --- |
| max_connections / max_user_connections | 151 / 0 |
| Threads_connected / Max_used_connections | 1 / 1 |
| Connection_errors_max_connections | 0 |

后面三项只是该次重启后的空闲快照，含本次查询连接，不能反推前轮压测峰值或排除压测时连接不足。下一轮在测量前后取同一实例的状态并记录观察期间峰值；不因当前空闲1连接就直接把上限调大。

按每个WSGI线程可能持一个Django连接估预算：`P×T + 单独worker/定时器 + 客户端准备ORM + 观测/管理连接 + 余量 ≤ 151`；这是配置预算，实际峰值仍须测量，应用额外线程/连接也须计入。1×32与2×16均以32个WSGI线程为起点，优先避免数据库容量变化混入进程比较。2×32可作为随后单独的总线程扩容实验；不直接跳到4×64再将连接拒绝解释成数据库整体不可用。HTTP `connection_limit=512`是Waitress连接channel限制，与MySQL151不是同一个参数。

## 6. 同机Python负载发生器的因果对照

现有[load_probe.py](D:/大三/课程/软件设计与开发/大作业/10_验收证据/06_B方案技术预研/实验代码/load_probe.py:125)使用一个Python进程的360线程闭环。它既读完整响应，又做JSON/CSV校验与版本更新；校验在已记录响应结束时刻之后，但仍延迟下一次请求，影响闭环吞吐与各类完成数。请求构造、Python调度与读取也可能影响客户端所见延时。由GIL机制可提出这些候选影响，不能据现有总CPU宣布已证实。

推荐逐项对照，不能同时改行列：

| 对照 | 服务端保持 | 客户端改变或保持 | 主要判读 |
| --- | --- | --- | --- |
| L：发生器分进程 | 固定1×32、相同观测 | 1×360线程 vs 2×180；全局worker分片不重复、同类别/门店/目标分布、校验不删 | 若客户端耗时/完成数变化而server app/SQL/queue近似，优先查客户端影响；负载到达率改变也会反向改变server排队，不能单看一个数 |
| S：服务进程拆分 | 1×32 vs 2×16，总WSGI线程相同 | 固定L中同一客户端方案及总360客户端 | 比较各进程queue/app、SQL/commit、连接峰值、请求失败与客户端完整响应P95，判断进程拆分的实际效果 |
| T：总线程扩容 | 2×16 vs 2×32；其余保持 | 与S相同 | 单独观察线程容量改变及数据库连接/锁竞争，不与进程效应合并 |

客户端拆分须先协调一次夹具准备，再给不同全局index范围；每个虚拟客户端保持自己的session、版本与独占成功负载目标。各进程用共同开始信号形成重叠的发起窗口，记录实际起止和排空；合并逐请求JSONL后按全量最近秩重新算每类P95，不能平均两个P95或简单平均吞吐。新增测量标签保留全部失败，不删除校验以获取漂亮成绩。

资源观测应区分登录准备、计时业务窗口和排空，对真实Python子进程采独立读时戳/单调时钟，按实际间隔算CPU变化。上一轮高CPU首两点属于登录准备，不能当业务循环证据；即使出现多核进程CPU，也不能只凭Python语言直觉判为统计错误或唯一GIL瓶颈。若同机各角色仍无法分离，再提出独立发压机的具体条件；该条件不是眼下补时序与做同机对照的阻塞。

## 8. 父代理新增诊断入口的只读口径核对

报告主体形成后，父代理通知已新增[serve_profile.py](%E5%AE%9E%E9%AA%8C%E4%BB%A3%E7%A0%81/serve_profile.py)、[profile_load.py](%E5%AE%9E%E9%AA%8C%E4%BB%A3%E7%A0%81/profile_load.py)，本代理实际只读查阅，未运行或改动。父代理正在做固定单服务进程32线程、1/6个客户端进程对照；本节是代码观测边界核对，不是对新负载结果的独立复算。

- 全局`range(part,concurrency,processes)`分片互不重叠，保留了原worker目标分配；公共Event和共享开始时间构成共同窗口。仍应记录各子进程第一条实际请求时间及完整排空。准备阶段每子进程8个登录线程，1/6进程的总准备并发不同，虽在计时窗口外，仍可能改变缓存/热身状态；解释对照时需注明。
- `queue`在调用原`add_task`之前记时，到`HTTPChannel.service`开始求差，包含dispatcher锁竞争、队列与调度，称“近似派发等待”准确。它不是TCP接收/解析之前的等待，也不覆盖客户端队列。当前闭环请求不做HTTP流水，此处可用作诊断；不是已完成的通用流水请求观测实现。
- `app`截止于`start_response`，代码已正确注明不是响应迭代/完整收包结束；SQL/commit包装在WSGI调用返回时恢复。当前非流式接口可观察其应用准备段，不能把它泛化为未来流式迭代的全部工作。SQL字段是驱动`execute`墙钟，含网络、驱动与调度，不等于MySQL纯执行或纯锁等待；连接建立、cursor准备及结果提取也未因此获得独立计时。
- `validation_ms`只包`validate`，不包括后面的响应头正则、数字转换、采样记录和下一次请求构造。它较低不能排除发生器其他Python/GIL开销。`X-PRE-Process-CPU`是整个服务进程所有并发工作的累计CPU，不能按两条请求的差值分配为单请求或单路径CPU；`outside_app`及再次减去queue的残差同样不能直接解释成某一瓶颈。

初次只读版本还发现失败保全边界：若某一类全部连接失败或缺失`sql_count`，对空列表求min/max会令汇总异常，原始JSONL当时又在汇总之后写入。本代理反馈后再次定点读到父代理已将原始行提前保存，并给min/max空集合设置`default=None`；因此不将它继续列为当前未处置缺陷，也未宣称运行轮实际触发过该故障。逐路径仍应同时报告计时字段覆盖数、HTTP失败与业务校验失败，防止仅有Server-Timing的成功子集被误认为所有请求的完整分解。
