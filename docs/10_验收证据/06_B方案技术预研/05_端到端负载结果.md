# PRE-03 完整HTTP响应短时负载结果

> 2026-10-21。Windows同机真实Django/DRF、MySQL与Waitress后端探针；属于性能预研。360并发短测仍未达到各项P95≤280ms，不认定正式AC-06通过。

## 1. 负载与统计口径

脚本为[load_probe.py](%E5%AE%9E%E9%AA%8C%E4%BB%A3%E7%A0%81/load_probe.py)，Waitress使用32线程、连接限制512。真实会话、CSRF、服务端授权及所需审计保留，计时到完整响应体接收；登录/样本准备在发请求窗口外，单独记录时间。客户端与服务端在同一台机器，没有浏览器/Vue渲染；硬件与锁定版本见[02环境说明](02_%E7%8E%AF%E5%A2%83%E4%B8%8E%E5%AE%98%E6%96%B9%E7%89%88%E6%9C%AC%E4%BE%9D%E6%8D%AE.md)。

数据子集为5家负载门店、6000个不同合成宠物引用、20000份正式病历。没有完整Pet实体模型，其他MQ等随机夹具门店不计入该子集。每店前台/医生/管理各1个合成账号，共15账号；360是并发虚拟客户端/会话数，不是360个不同员工账号。

五种客户端固定分工：接待、查询、包含护栏校验及提交的诊疗写、用药追加、单份CSV导出。客户端为闭环，完成一个请求后发下一个，因此五类客户端数相近不保证最终请求数占比相同；独立记录避免把同一目标的故意竞争当正常负载。用药更正、建议采纳不在本轮负载路径中；导出每次仅1份授权病历，响应593B，不是导出全部负责病历。功能与并发锁负向样本另见03。

15秒为新请求发起窗口，窗口后排空在途请求；成功吞吐=成功样本数/包含排空的墙钟秒数×60。P95按所有样本的最近秩`ceil(0.95N)`，失败不剔除，逐路径报告；完整逐请求JSONL保留时间、状态、字节及worker，无认证凭据。该闭环短测与同机发压限制均须在正式协议中重新审定。

原始文件为`baseline_{10,60,360}_summary.json`及同前缀`_samples.jsonl`。360初始测量保留870个ConnectionError，不能写为零失败；后续5秒诊断`connection_diagnostic_360`为1452样本、251失败，记录WinError10061连接被拒。初始样本未逐条保存相同详细原因，因此不能反推870条全部已一一定位。

响应头诊断发现JSON缺Content-Length，使用chunked并关闭连接；CSV已有Content-Length并可复用。加入Django CommonMiddleware给非流式响应设置长度，先保存回归红灯再修正，重启HTTP后复测。前后头信息见`before_content_length_response_headers.json`及`after_content_length_response_headers.json`。

CommonMiddleware的机制依据为[Django官方文档](https://docs.djangoproject.com/en/5.2/ref/middleware/)。本轮本机证据只能说明修正后连接现象和复测结果：期间也加载了安全修正，数据/缓存未重置，请求占比显著变化，不能把所有时延差异唯一归因于这一项。

360档导出占比由初始2499/3796（约65.8%）变为621/3133（约19.8%），较慢路径获得更多完成样本。CSV的P95没有随其他路径一起改善，不能称“全部路径全面提速”。60和360档五项P95均超过280ms；成功吞吐数值高于800/分钟不能抵消时延未达标或短测时长不足。

## 4. 一次资源诊断

在正常数据库重启比较完成后，单独再跑360客户端、10秒发起窗口，并同时只读采样实际HTTP/MySQL/MQ及负载Python子进程；该轮额外受采样开销影响，不与15秒对照混为同一实验。

结果[resource_diag_360_summary.json](%E5%8E%9F%E5%A7%8B%E7%BB%93%E6%9E%9C/resource_diag_360_summary.json)：2116样本、0失败，含排空12.047秒，10538.85成功次/分钟；五项P95依次3072.46、3288.81、2937.96、3225.27、2996.68ms。资源原始文件为[resource_diag_resources.json](%E5%8E%9F%E5%A7%8B%E7%BB%93%E6%9E%9C/resource_diag_resources.json)，35.082秒内23个非等间隔样本，15个采到实际发压子进程；28个逻辑处理器。采样起止及CPU累计秒必须按实际UTC差计算，不能把累计CPU直接当CPU百分比，也不能采venv启动器代替实际服务进程。

此次观测只为下一轮定位提供线索，未单独测出每条SQL/锁/提交/请求排队时间，也未分离同机客户端资源影响，不能宣布“数据库慢”“框架不行”或已唯一定位瓶颈。

尤其首两点HTTP累计CPU增量较高，但两点均在06:35:33.284 UTC业务计时开始之前，属于并发登录准备阶段。进程CPU字段为所有处理器累计秒；近似23.63核未超28核预算，却不能用于认定业务循环瓶颈。具体语义、时点误差与峰值RSS见02§7；不由该短观测推断GIL行为。

## 5. 正式验收差距与下一步

本轮没有360并发持续10分钟，没有全量正式业务/前端、独立校验接口、用药更正及建议采纳混合路径，没有大授权集合导出/并发更正一致性专项，也未关闭SRS TBR-05正式协议。实验子集虽达到5店/6000引用/2万病历数量口径，不等于完整业务数据模型及分布等价。

下一步保持需规数字和已验证的审计/授权原则：先分离客户端与服务端资源、补SQL/事务/连接/排队观测，比较单机入口的进程/线程和连接预算，再按同一分布复测；补大授权集合CSV、并发更正、各写路径。详细前置任务见[04目录07](../../04_%E8%AE%BE%E8%AE%A1%E4%B8%8E%E6%8E%A7%E5%88%B6%E6%96%87%E4%BB%B6/07_B%E6%96%B9%E6%A1%88%E6%80%A7%E8%83%BD%E6%94%B6%E5%8F%A3%E4%B8%8E%E5%AE%9E%E7%8E%B0%E5%89%8D%E7%BD%AE%E4%BB%BB%E5%8A%A1.md)。不能删审计、缩小授权导出或降低题定目标后仍宣布通过。
