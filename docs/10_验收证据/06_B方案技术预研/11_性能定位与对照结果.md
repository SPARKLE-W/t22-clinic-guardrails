# 性能定位与对照结果

> 2026-10-21；本轮为第六阶段增量实验。保留原有负载结果与08历史检查点，不把新增观测当正式AC-06。

## 1. 本轮计划与判据

先固定同一Django服务/数据库和Waitress单进程32线程，加仅回环诊断入口`serve_profile.py`。逐请求记录服务调用到start_response的app耗时（含Django渲染与事务commit，不含后续响应迭代发送）、SQL execute墙钟、独立commit墙钟及SQL次数。用Waitress3.0.2本地实现的受控子类，从dispatcher.add_task对channel记时间，在channel.service开始取差，作为调度等待近似值；脚本不使用HTTP流水线，每channel同时只有一请求。

客户端计时仍到完整响应体接收。每请求先求完整时延减app的区间外耗时，再算P95，不能用两个P95相减；即使另有dispatch观测，剩余仍含HTTP解析/收发、调度和客户端开销，不一概归为队列。SQL墙钟包含数据库、网络及锁等待，不能冒称纯SQL CPU。

使用`profile_load.py`统一全局worker索引选独立目标，所有子进程登录准备好后才进入共同窗口；第一组单进程总360线程，第二组多进程仍总360线程。服务端代码、线程、连接预算和五类工作负载保持相同；合并所有逐请求样本后算P95和排空吞吐，不能平均子进程分位数。两组均为闭环，记录实际路径占比、在途并发及子进程CPU，不能由吞吐改善单独推断GIL。

证据保存在`原始结果/性能定位`，结果标签不覆盖。对照先回答瓶颈在哪，再决定是否需要单机多工作进程入口。完整导出与并发更正测试由独立test库承接，详见10报告。性能目标保持各项完整响应P95≤280ms；未执行360并发10分钟正式验收。

## 2. 实际分段和进程对照

各轮均为360个全局独立worker、10秒发起窗口加排空，原始JSONL保留全部请求。以下五路径顺序为接待/查询/含护栏诊疗写/用药追加/单份CSV。

| 实验标签 | 发生器/服务器 | 请求/失败 | 含排空秒数 | 成功次/分钟 | 五路径完整响应P95 ms |
| --- | --- | --- | --- | --- | --- |
| client1_server1_360 | 1 / 1×32线程 | 1957 / 0 | 12.111 | 9695.37 | 2719.30 / 2885.78 / 3377.42 / 3259.59 / 3228.37 |
| client6_server1_360 | 6 / 1×32线程 | 2021 / 0 | 12.196 | 9942.20 | 3383.77 / 3396.31 / 3411.81 / 3895.08 / 3823.60 |
| boundaries_client6_server1_360 | 6 / 1×32线程，增加边界时间戳 | 1945 / 0 | 12.191 | 9572.32 | 2420.33 / 3555.72 / 3528.58 / 3605.27 / 3578.99 |
| client6_server2_360 | 6 / 2×16线程，总线程仍32 | 3658 / 0 | 11.058 | 19847.89 | 1935.92 / 1940.84 / 1969.05 / 1979.79 / 1977.62 |

先有10客户端5秒smoke，861样本0失败，用于确认时序头、真实SQL/commit均可见，不与360档混算。1/6客户端进程对照没有支持“多进程发生器明显解决时延”的结果。六发生器固定后，服务器从1×32变2×16的吞吐约翻倍，但完整响应仍未达到280ms。没有删除必要审计、身份检查、完整响应计时或业务校验。

多进程发生器每进程准备时使用8个登录线程，总准备并发不同；准备在计时之外，仍可能影响缓存/热身。各轮数据持续累积而未复位，也不是随机重复试验。小CSV始终593B；保留闭环下实际请求比例，不能据一次对照宣布唯一根因或普遍性能倍数。

## 3. 延迟现在定位到哪里

在后两轮增加App-Start/App-End的`perf_counter`时间戳，逐请求与同机客户端起止关联。[Python3.12官方说明](https://docs.python.org/3.12/library/time.html#time.perf_counter)明确该时钟在进程间一致，Windows自3.10亦如此；这里只用于本机诊断，不能移植成跨机器单调时钟相减。

| 计时区间 | 六发生器单服务 | 六发生器双服务 |
| --- | --- | --- |
| 各路径“应用开始前”P95范围 | 2294.72—3530.66ms | 1865.65—1894.95ms |
| app P95范围 | 164.50—209.51ms | 87.17—119.60ms |
| dispatch P95范围 | 47.33—52.01ms | 32.93—36.14ms |
| 应用结束后至完整接收P95范围 | 13.31—15.53ms | 8.20—9.73ms |

这些是各路径分位数的范围，**不能相加或彼此相减组成另一项P95**。主要长延迟落在应用计时之前，尚未拆开客户端发起/连接、HTTP接入解析及调度的各段。dispatch几十毫秒不足以解释整段数秒；不能直接称为“Django队列慢”或“MySQL慢”。app低于280ms也不能代替完整响应要求。

响应头给出的实际进程累计CPU以首末离散样本近似折算：单服务约1.19—1.22核；双服务各约1.19、1.22核。发生器业务/排空窗口CPU总量约0.18—0.34核；它不包括准备期，也不代表没有瞬时调度开销。未作独立峰值RSS测量，不由这些平均观察推断GIL或唯一瓶颈。

双服务是客户端按进程分片直连18722/18723的诊断，**未验证统一反向代理入口**，不是正式部署或微服务改造。实际连接上限151及单机入口候选依据见[09工程报告](09_%E6%80%A7%E8%83%BD%E5%AE%9A%E4%BD%8D%E5%B7%A5%E7%A8%8B%E4%BE%9D%E6%8D%AE.md)。独立复算及计时恒等关系核对见[06审查§7](06_%E4%BA%A4%E5%8F%89%E5%AE%A1%E6%9F%A5%E4%B8%8E%E7%BB%93%E8%AE%BA.md)。

## 4. 大范围导出的独立修正

进程对照结束后才修改`services.py`的导出加载；此前源保留为`原始结果/性能定位/services_before_batch_export.py`，不能用后续CSV优化解释上表的吞吐变化。

4000份授权病历的查询预算先真实失败：8010条SQL、5755.893ms，仍完整输出1698887B/8003行。共享父锁之后把每记录两次查询改成两个完整集合批量查询，按record_id分组后保留原排序、版本/更正链、发送前重新授权及完整审计。修后独立3项通过，非竞争导出12条SQL约669.831—846.163ms；真实锁等待样例1717.146ms含故意等待，不当作纯导出速度。该查询预算只用于本轮防N+1，不改需规数字。

随后完整实验回归 **40项通过，101.421秒**，见`原始结果/batch_export_full_regression.txt/.json`；原37项加3个大集合测试，不重复计数。SQL/集合/并发细节和角色代理只读复核见[10报告](10_%E5%A4%A7%E8%8C%83%E5%9B%B4%E5%AF%BC%E5%87%BA%E4%B8%8E%E5%B9%B6%E5%8F%91%E4%B8%80%E8%87%B4%E6%80%A7.md)。[Django优化说明](https://docs.djangoproject.com/en/5.2/topics/db/optimization/)支持先测量并一次取回所需集合；本机收益依据为实际红灯/修正/绿灯，不由官方文档代替测试。

再以真实医生会话通过HTTP导出其load_0全部4000份正式病历，完整收到3093219B、12296行（6876历史、1420用药），4000当前记录无漏无重、版本/历史数量及4000审计目标均一致，完整响应 **776.151ms**。见[单次HTTP原始记录](%E5%8E%9F%E5%A7%8B%E7%BB%93%E6%9E%9C/%E6%80%A7%E8%83%BD%E5%AE%9A%E4%BD%8D/large_4000_HTTP_batch.json)。这不是P95、混合360并发或正式验收；其历史分布不同于test库1698887B样本，不把两者当严格前后时延对照。

## 5. 当前出口和下一步

本轮得到两项可执行结论：大集合导出的逐记录查询已修正，完整性和并发边界回归通过；单进程入口容量不足的风险有对照支持，下一步比较4×8等单机进程配置并验证统一入口，继续区分接入前耗时，不能凭双端口对照就冻结部署。先固定新的批量导出代码做新对照，不把不同代码阶段拼成一组成绩。

仍缺正式独立校验/用药更正/建议采纳混合负载、持续10分钟、正式测量协议和完整产品。第08文件保留前一检查点；本轮源码、原始样本、基线及最终关闭状态由[12增量检查](12_%E6%80%A7%E8%83%BD%E6%94%B9%E8%BF%9B%E8%AF%81%E6%8D%AE%E4%B8%8E%E5%9F%BA%E7%BA%BF%E6%A3%80%E6%9F%A5.md)记录。SRS v1.0保持原样；停止实验进程后保留数据及可复现脚本。
