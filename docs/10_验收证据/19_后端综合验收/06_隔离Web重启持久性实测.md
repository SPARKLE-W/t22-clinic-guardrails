# NFR-05 隔离 Web 重启持久性实测

2026-10-24，在第二轮正式负载结束后，针对**独立合成库** `t22_perf_20261024_r2_test` 和 `127.0.0.1:18830` Web 进程做重启试验；不触碰共享 18730 服务及其应用库。该库已被正式负载及后续无预热诊断修改，故本试验只核对这些**已提交数据**在 Web 进程重启前后保持一致，不重新解释负载结果。

## 步骤与原始证据

1. 使用仓库外临时脚本读取六张持久化表的行数，并对按 ID 排序的前100条病历版本、前100条审计事件计算 SHA-256；事后将同等逻辑整理为[可复跑脚本](%E6%A3%80%E6%9F%A5%E8%84%9A%E6%9C%AC/14_%E9%87%8D%E5%90%AF%E6%8C%81%E4%B9%85%E6%80%A7%E5%BF%AB%E7%85%A7.py)。脚本只输出计数和摘要，不输出临床正文或数据库口令。原始输出为`原始结果/restart_before_01.json`。
2. 确认端口 18830 的原 Web 进程 PID `70988` 后停止该进程。第一次重启选错 Python 环境，缺 Django 导致服务未启动；记录为操作失败，未当作通过。改用项目依赖环境启动新 Web 进程 PID `52744`，`GET /app` 返回 200。
3. 在任何新业务请求前用同一临时脚本再次读取，得到`原始结果/restart_after_01.json`；两份 JSON **逐字相同**。
4. 随后用合成医生账号通过真实 `/api/login` 登录，并对其负责接诊调用 `/api/clinical/encounters/{id}`：登录 200、病历读取 200、返回 JSON；仅保存状态、类型和响应 SHA-256 于`原始结果/restart_api_01.json`。这一步会新增正常登录/读取审计，因此在步骤3的快照比较之后执行。

| 核对项 | 重启前 | 重启后（业务请求前） |
| --- | ---: | ---: |
| 接诊 | 24049 | 24049 |
| 正式病历 | 20000 | 20000 |
| 病历版本 | 26076 | 26076 |
| 审计事件 | 27058 | 27058 |
| 告警待发/状态记录 | 12000 | 12000 |
| 投递回执 | 12000 | 12000 |

病历版本样本 SHA-256 两侧均为`47198B82F75DE1AE6B9ED851C80107AE553E36D3A042F5C37CAEFB7C5FCF1572`；审计样本两侧均为`811D7F6310AA1692CC2FC8430A4D9CADEDD900BDC103691E91635234F3F8CB94`。试验前后的源码包含同一数据模型，但 Web 进程从第二轮负载时的 `57b32a3` 更新为当前后端分支；这是一次升级式重启，未涉及新迁移。

判定：本轮支持“已提交病历、审计及告警相关记录在**Web 进程重启**后仍在数据库中，且医生可再读取负责病历”。它不覆盖 MySQL 故障/恢复、RabbitMQ 故障/补发或断电写入中的事务；这些路径按原独立测试和后续总体验收分别核对。预置投递回执中含明确标注的合成数据，行数稳定不证明 12000 次真实消息投递。
