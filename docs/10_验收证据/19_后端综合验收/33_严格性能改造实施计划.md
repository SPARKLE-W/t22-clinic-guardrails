# TBR-05 严格性能改造实施计划

> **执行代理：** 按本计划逐项实现、复核和记录证据。来源为本人冻结的[正式负载测量协议 v1.0](01_正式负载测量协议_v1.0.md)、[当前问题总结](32_当前问题与测试总结.md)及 2026-11-03 收到的《T22_性能改善方案》提案。提案不是需求或实测结论。

**目标：** 保持权限、临床版本、导出字节与审计要求，在同一版本的完整云端窗口内证明 360 个持续在途请求、300 秒预热、600 秒正式、每分钟至少 800 次成功、七类完整响应 P95 均不超过 280 ms、授权请求零失败；未达标则保留原始数据并明确瓶颈。

**架构：** 继续采用 Django/DRF、MySQL、RabbitMQ 与独立发送机。先降低应用和数据库每请求成本，再用受控资源对照判断是否需要更多 CPU 或更高云盘性能。每项改动保持可独立审查的 PR。

**现时边界：** 服务器目前关闭。先完成代码改造、本地回归、CI 与部署文件准备；不得连接服务器、启动云端诊断短测或清理任何旧库。代码候选稳定且用户启动服务器后，再重核主机身份、隔离库、连接预算、磁盘性能和进程状态。云端负载只运行冻结协议的完整正式窗口。

## 提案审查与取舍

| 提案 | 当前判断 | 执行条件 |
| --- | --- | --- |
| A1 导出 CSV 构造移出事务 | 采用；可缩短事务持有时间，但涉及读取与审计边界 | 物化读取后生成完整字节；第二事务重新核验账号并写登记/审计，提交成功后才返回；回归权限撤销、审计失败、并发版本追加 |
| A2 审计目标主键改自增 | 不执行该描述的迁移：`AuditTarget` 已因 `DEFAULT_AUTO_FIELD=BigAutoField` 使用自增主键 | 先用实际 SQL 与索引统计定位 4,000 行写入成本；保持逐记录关联，评估批量大小和索引后再决定 |
| A3 4,000 UUID 查询分块 | 待测；分块增加往返次数，收益并无现证据 | 比较单次 IN 与分块相同数据库/数据/输出的 SQL 与完整响应成本；有净收益才合入 |
| A4 取消读接口 COUNT | 不直接删除：`total` 是现有接口字段 | 保持精确 `total`；先检查显式单病历读取实际 SQL，优化不改变总数语义的重复取数 |
| A4 缓存模板验证/审批 | 暂不缓存审批结果：跨进程撤销与启用一致性难保证 | 只考虑不可变模板结构解析缓存；必须验证规则变更与审批撤销实时生效 |
| A5 写入校验移出事务 | 分离纯计算与依赖数据库状态的校验 | 锁/版本冲突/错误码顺序回归；只移动经证明与当前数据无关的步骤 |
| A6 连接复用与进程布局 | 作为部署候选，不宣称当前已生效 | 所有进程线程数、MySQL最大连接、健康检查和余量必须同一次预检核算；以完整窗口校验 |
| A7 CSV 热路径 | 待剖析再改；保持逐字节输出 | 同一 4,000 份夹具比较字节、SHA-256、审计与峰值内存 |

提案用 `360 / 0.28` 推导每秒至少 1,286 次并给出 16/32/48 核表，只能作容量情景估算：P95 不能直接推出平均响应，Run5 的约 37 ms 是不同进程 CPU 秒与成功请求数的粗略聚合，不能据此承诺固定核数。提案的 A1、A3、A7 收益数字也须由同一源码和夹具实测确认。不得减少导出范围、审计粒度、真实会话或完整体计时来改变冻结目标。
