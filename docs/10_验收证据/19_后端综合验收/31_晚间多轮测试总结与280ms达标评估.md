# 晚间多轮测试总结与 280 ms 达标评估

> 日期：2026-10-31。依据冻结的 TBR-05、本目录中记录的 round31—round36 诊断摘要，以及已归档的两轮正式实测。本文区分任务书原始要求、项目冻结的测量协议和本晚诊断轮；不把诊断轮写成验收，也不把连接失败轮的分位数解释为系统性能。round36 原始客户端文件截至2026-11-01在记录所指本机目录中未找到，故精确时间线不能从原始请求复核。

## 1. 结论摘要

- 两轮有效的完整正式测量（2026-10-24）都证明了 360 个在途请求、十分钟逐分钟吞吐高于 800、正式业务请求零失败；但七类完整响应 P95 约为 11.8—33.6 秒，全部未达 280 ms。
- 另有 2026-10-25 的 AC-06 课程活跃会话 v1.1 试验：360 个活跃登录会话、正式 600 秒、10774 次请求、零失败，各组 P95 为 65.1—138.4 ms；但实际请求在途 P95=3、峰值12，且不是当前冻结的 360 持续在途协议。它证明了一个并发定义下的结果，不能替代另一个定义。
- 本晚 round31—round35 是约 60 秒诊断/预检，不替代正式窗口。零失败轮的七类 P95 仍为约 4.0—14.5 秒；round32 有 11 个客户端断连。
- round36 按 300 秒预热＋600 秒正式窗口启动，但正式段 96,864 个请求有 94,992 个（98.07%）连接重置失败，约运行 361 秒发生连接集中重置。该轮无效，不能使用其中约 2.08 秒的 P95 作为性能结果。
- 280 ms 是当前最主要的未通过项。吞吐下限本身不是瓶颈：早先两轮正式测量每分钟完成约 1,398—2,161 次；360 在途下的完整响应 P95 才是主要差距。
- 现有证据支持优先查服务器入口排队、CPU/并发执行与同步数据库/审计成本；证据还不足以断言某一个因素独占瓶颈，也不足以判定 280 ms 不可达到。任务书不允许服务拆分和集群编排，所以第一选择应是在原单体/单机边界内做可测的运行配置、代码和垂直资源改进。
- ECS 因欠费停止或异常，服务端无法读取第36轮故障时刻的任务、进程和系统事件。充值并恢复可达前，不再发起云端负载。

“P95≤280 ms”意味着在相应正式负载下，每个规定请求组至少 95% 的授权业务请求在 280 ms 内完成；它不是平均时延，也不表示吞吐只需刚过 800/min。TBR-05 的固定并发、请求比例和完整 CSV 使它成为比单接口短测更严格的容量目标。

### 已有活跃会话结果与严格在途结果不可互换

[AC-06 课程活跃会话 v1.1 完整试验](24_AC06%E8%AF%BE%E7%A8%8B%E5%8F%A3%E5%BE%84v1.1%E5%AE%8C%E6%95%B4%E9%AA%8C%E6%94%B6.md)在其明示口径下，查询、护栏、接诊、病历写入和三类 CSV 的 P95 均低于 280 ms，十分钟吞吐和零失败也达到预定值。但它使用的源码早于本次最终源码，实际 HTTP 请求在途远低于360，且未覆盖1000—4000条大导出，因此目前只是一份“该协议版本、该源码与该环境下通过”的证据。它**不证明**当前最终源码通过 TBR-05，也不证明 360 个请求同时在途时达标；任务书是否按活跃会话解释仍须由课程判定者确认。

### 重要诊断结果

- round31—round35 是短测。round35 的 P95 已比旧 360 短测略有改善，但仍约为门槛的 20—40 倍。
- 目标池缺陷已修：20,000 条记录被拆为互不重叠的护栏 6,670、诊断更正 6,665、采纳 6,665；演示建议脚本幂等补足。round36 目标计数没有达到池上限，因此不能用目标耗尽解释连接中断。
- round35 小型临床导出（1—20 条）响应体中位约 6.4 KB，P95仍为10.29秒；1000—4000条组响应体中位约1.48 MB、时长P50约6.81秒。小响应也很慢，说明仅减小 CSV 不能解决整体延迟。
- 1.48 MB 经 100 Mbps 链路的理论无开销发送时间约 118 ms；2.46 MB 约197 ms。带宽会限制大导出剩余预算，但小响应同样慢，不能把主要故障简单归因为出口带宽。
- round30 服务器资源原始 CSV 的75个样本中，CPU P95/峰值均100%，可用内存最低约25.3 GiB；写入延迟 P95为17.153 ms，写操作速率 P95为2849.7、最大3840.7。CSV没有读IOPS、盘符/云盘ID映射或云盘PL，写操作速率不能直接当成云盘总IOPS；这些数据与round36事件也没有可复核的同窗时间线。round22 的 MySQL 语句累计时间中，COMMIT 平均约20.9 ms，审计目标批量 INSERT 平均约19.0 ms。合并看，CPU排队和磁盘写压力都应纳入下一轮实测；现有数据仍不证明单一根因。
- 先前观测到的 MySQL TIME_WAIT 端口耗尽已由连接复用显著缓解；把 `max_connections` 从400提高到800没有消除原错误。round31—round35 的零失败短测说明连接复用有稳定性价值，但没有把 P95 降到目标。

## 4. 对 280 ms 的总体判断

### 不是目前已证明的框架/架构上限

两轮正式测量与多轮短测都表明系统功能链路可以在 360 在途下持续运行，且历史正式轮吞吐超过800/min；但长尾响应远高于目标。当前证据说明实现/执行环境容量不足，不足以证明 Django＋MySQL＋RabbitMQ 必须整体替换。

T22 任务书 §3 对本题架构有边界：不做服务拆分/集群编排，数据使用单机数据库及本题中间件。因此不把拆微服务、集群、读写分离或改成异步任务号返回作为本次达标方案。单机范围内仍可优化事务与序列化、数据库访问、Waitress 进程/线程配置和垂直扩容；是否需要提高单机 vCPU，要由稳定正式基线的 CPU/排队证据决定。

### 实际达标路径取决于最终验收采用哪种并发定义

1. 若老师按任务书的“360 个并发用户/活跃会话”理解，最短且诚实的路径是：先把 v1.1 的并发定义、15—25秒操作间隔、请求混合、实际在途、未包含的大导出范围和代码提交明确交给课程判定者；若该口径被接受，在**当前最终提交**上复现完整十分钟、逐请求全响应体计时、零失败/吞吐/P95/导出摘要校验，保留原始数据。这是复核一项已有的课程口径成绩，不是把 TBR-05 改称通过。
2. 若最终要求就是已冻结的 TBR-05（360 个请求持续在途且包含大范围导出），目前没有可报告的达标轮。须恢复稳定服务器后先定位排队与断连，再通过逐级并发分段计时和单变量优化降低真实完整响应时延；只有同一最终提交完成 300秒预热＋600秒正式轮、七组各 P95≤280ms、逐分钟吞吐和零失败全部通过，才算达标。
3. 在口径未获确认前，应同时保留这两项结果与限定，不挑较容易的一项覆盖另一项。不能凭活跃账号数宣称 360 在途，也不能把失败的 TBR-05 结果删去。

### 短板优先级

1. **先修复运行稳定性。** round36 的客户端错误从正式窗口开始出现，约运行361秒后在途连接集中重置；之后四条 SSH 转发和 ECS 管理端口均不可达。第36轮无法读取 Windows 计划任务结果、Waitress/Caddy 退出原因或系统重启/网络事件。因欠费造成 ECS 当前不可用与该轮的故障时间线是两件事，不能混为一个已证实根因。
2. **再查入口排队与 CPU。** 360 短测中查询、接诊、护栏、写入和小导出一起变慢；同轮 8×45 对照没有改善。历史 CPU P95为100%，所以需要入口等待、应用服务时间、SQL/锁等待、审计提交、CSV生成和响应发送的分段时间，不能只再加线程。
3. **事务/数据库开销作为定点候选。** 事务提交和审计插入有可量化成本，但目前没有证据说明删除锁或异步审计能安全达标。应分别测 `PolicyHead`/接诊锁等待和 SQL 时间，保持病历、规则版本与审计一致性。
4. **导出是附加约束而非唯一原因。** 4,000条单次完整导出曾测得约0.93—0.96秒；大文件和 100 Mbps 出口会压缩 280 ms 预算，但本晚小导出、非导出组也同样多秒，所以先消除全局队列/资源争用，再对大导出专项优化。

### 达标可能性

以当前 8 vCPU、32 GiB、100 Mbps 的单机候选，历史短测没有证明能达到 280 ms；也没有证据证明任何单机配置必然达不到。CPU饱和意味着同机 vCPU 竞争值得实测，内存与磁盘目前不像第一瓶颈。稳定后可先在单机架构内对比基线与更高 vCPU 配置，并同时记录每类请求的完整响应 P95、CPU、队列深度和 DB 时间。性能变化不应从 vCPU 倍数线性推算；若垂直扩容/代码与配置优化后仍不达标，须按真实差距报告，不能靠降低混合负载、取消导出审计或只统计响应头来“达标”。

## 5. 充值后恢复与多轮改进顺序

### A. 先恢复 ECS 并确认 round36 根因

1. 充值后只按控制台状态启动/恢复 ECS；SSH 可达后先读取系统事件、任务计划 `LastTaskResult`、Waitress/Caddy进程日志及启动时间，查连接重置点是否对应任务超时、进程退出、主机停止或网络事件。
2. 核对并收尾 round36 的临时服务、测试专用 MySQL 连接上限、测试配置、计划任务和 Caddy 原始日志；先查找客户端原始文件的其他备份。若无法恢复，则保留既有汇总并明确标注逐请求时间线不可复核，不根据事件时间重构测试起点。含会话/CSRF的服务端原始日志只抽取必要统计后删除。确认普通演示库和 RabbitMQ 权限仍为原值。
3. 以固定隔离夹具、连接复用配置、16×23布局做20分钟仅健康端点稳定性探针；SSH、四条隧道和17个回环监听连续稳定后才进入负载预检。

### B. 基线、归因、改进

1. 执行60秒360混合预检，检查零失败、目标池不耗尽、实际在途与四隧道稳定；若任一失败，停在诊断阶段。
2. 用最终源码和可重建夹具做1、30、90、180、360并发对照；至少为查询、护栏、接诊/写入和三类导出按大小记录入口等待、应用耗时、SQL/锁、审计、CSV、完整响应发送和主机资源。短探针只用于定位。
3. 每轮只改一个瓶颈：先用剖析和队列数据确认是 CPU/WSGI 线程、规则校验、SQL/锁、同步审计还是 CSV/传输；再决定代码优化或同一单机内垂直扩容。复用连接保留为稳定性配置，不声称它解决时延。
4. 每个候选都跑完整后端回归、相同夹具和60秒360预检。只有零失败、服务稳定、各组延迟确有改善才保留；未改善即回滚并记录。
5. 只在最终候选稳定后按冻结 TBR-05 再跑300秒预热＋600秒正式窗口；逐分钟验证≥800、360在途、七类P95≤280ms、零失败和完整导出校验。失败/断连均计失败并保留原样。

## 6. 结论与当前状态

AC-06/TBR-05 目前未通过，且 round36 没有产生可用的正式 P95 结果。有效历史正式轮证明了吞吐与零失败，但未证明延迟目标；本晚短轮确认目标池和16×23比8×45更适合作为下一候选，仍远未达标。充值恢复 ECS、查明约361秒连接中断原因，是下一步云端工作的必要条件；在此之前不把未知根因写成结论，也不按短测宣布完成。
