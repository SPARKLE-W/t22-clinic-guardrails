## 2. 先纠正主体与文档边界

任务书FR-05的“医生仅能读写本人接诊病历”，其中“本人”是登录医生角色相对于记录归属的指代，不是学生开发者，不是医生作为患者，也不是宠物主人。需规正文改写为：

> 系统仅允许当前登录医生账号读写其在所属门店负责接诊的宠物病历；对其他医生负责的病历或其他门店的病历请求，系统应拒绝并记录原因。

宠物是诊疗对象；宠物主人是业务相关方及信息来源，不因与病历有关就自动成为登录角色。用户本轮明确选择“澄清措辞和边界，按任务书三角色”，因此不增加主人端。

开发者、教师、主代理与子代理是项目参与者，不是VetRules的运行角色。人机协作计划、原始问答和审查处置放07/10目录；系统自身按FR-03提供的人机分工登记功能仍须写入产品需求，不能因清理协作记录而删掉该功能。

## 3. T22需规的裁剪结构

下表是结合来源、课程与T22制定的项目结构，**不是宣称逐条抄自ISO目录**。

| 内容块 | 要回答的问题 | 不能混入的内容 |
| --- | --- | --- |
| 文档控制与来源 | 目的、适用范围、版本、状态、依据、变更和来源类型 | AI自报“已定稿”、与真实审批无关的签名 |
| 背景目标与系统边界 | 为什么做、服务谁、做与不做、依赖和假设 | 自行扩展主人端、收费/预约/完整医院信息系统 |
| 术语、用户与上下文 | 三类账号、宠物/主人/记录归属的区别、外部交互 | “本人”“我方”等不明确指代；把学生或代理列为运行角色 |
| 业务规则与权限 | 门店、接待/接诊归属、字段可见性、统计/告警/审批/审计边界 | 用界面隐藏代替权限要求；自设管理全文特权 |
| 用例与功能要求 | 目标、触发、前后条件、输入、主要/异常场景、可观察结果 | 将一个功能名当完整用例；为凑数添加无来源功能 |
| 数据与状态要求 | 逻辑含义、关联、必需留痕、版本/追加/采纳/告警状态 | 过早固定物理表、ORM类、索引或最终JSON结构 |
| 接口要求 | 页面/服务/数据/消息边界，输入输出及失败语义 | 把具体URL、函数、数据库事务代码当唯一需求实现 |
| 非功能与既定约束 | 题定容量、性能、恢复、安全、维护性及单机分层边界 | 删除题定技术约束；自行降低数字或声称已实测 |
| 验收与追踪 | 来源→需求→用例/验收，设计/代码/测试随后回填 | 只列AC而漏FR/NFR；把总覆盖率代替行为证据 |
| 未决项与冻结条件 | 哪些缺口、影响、谁确认、何时必须闭合 | 沉默即通过、为了“无TBD”而编造答案 |

## 4. 每条要求的写作与审查规则

1. 以“系统应……”表达系统义务，明确对象、条件、结果；一条只承担一个可验证意图。角色目标可放用例，开发任务放计划。
2. 沿用FR-01—08、AC-01—08及已建立NFR编号；必要时加子编号，不重排来源编号。区分任务书原文、经确认的演示约定、待审提案和工程实现建议。
3. 数据字段是业务定义，数据库表、索引、服务类与代码调用属于设计；任务书锁定的单机、分层、统一权限等约束仍属于需求输入。
4. 每个用例至少包括参与角色、目标、前置/触发、输入/输出、主场景、拒绝/异常、后置与关联要求。图、表、正文必须一致；PlantUML源不能宣称已渲染审图。
5. 权限按登录身份、门店、接待/接诊归属、操作与字段范围表达；同一宠物历史记录不自动授予新医生或前台。拒绝请求要有可验的记录要求。
6. 非功能保留全部题定数字，并定义测量对象和待明确口径；不把未测值写入“通过”。压测和覆盖率详细操作另在测试方案承接。
7. 修改需规必须保留变更理由及必要快照；原始任务书和旧审查证据不改写。需求基线冻结之后仍可受控变更，不存在AI自行宣布的永久“最终版”。

## 5. 分工与必读输入

三位代理和主代理在本轮均须先读：本目录AGENTS.md、T22任务书摘录、可信汇总通用要求、本文件、当前03需规。不得仅凭上轮审查记忆判断。

| 审查视角 | 本轮负责检查 | 输出边界 |
| --- | --- | --- |
| 模拟教师 | 是否覆盖课程/T22、原文与提案是否准确、基线条件是否充分 | 不编造教师偏好，不给真实评分或认可 |
| 模拟业务阅读（原模拟学生） | 术语、三角色/宠物/主人/开发者区别，用例是否能读懂 | 不代替真实医院，也不把代理建议记作真人决定 |
| 工程证据 | 行为是否可验证、数据/状态/接口与权限的一致性、需规设计分界 | 不把实现方案反灌为既定需求，不承诺尚未实测的可行性 |

代理收到本文件后应在审查开头确认已读，先对结构和边界审查，再对修订稿定点复核；本轮输出放10目录的新阶段文件，不覆盖之前需求讨论记录。

## 6. 草案、评审稿、冻结基线的区别

- **草案**：结构、场景和未决细节尚在补齐，不作为全面编码依据。
- **评审稿**：内容已足够逐项核对，但仍可能有未解决问题；代理意见不是批准。
- **冻结基线v1.0**：任务来源完整、角色/权限无歧义，关键业务与字段/接口边界确认，必要用例及验收可追踪，阻塞问题关闭，真实项目负责人确认该版本作为设计输入并留存版本/哈希。

冻结基线是项目内部决定，不等于真实老师或医院审批、系统验收通过。未来变更要做影响分析并同步设计、实现和测试。本次v0.2及即将修订的v0.3都不是最终冻结基线。
