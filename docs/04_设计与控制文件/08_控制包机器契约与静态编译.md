# 控制包机器契约与静态编译

> 2026-10-22；v0.2实现契约。承接SRS v1.0与01/02设计，本批仅完成离线静态编译。业务角色、权限及需求指标不变。

## 1. 输入、来源和边界

正式实现入口为[05代码说明](../../05_%E7%B3%BB%E7%BB%9F%E4%BB%A3%E7%A0%81/README.md)，新输入为[完整定义v0.2](../../05_%E7%B3%BB%E7%BB%9F%E4%BB%A3%E7%A0%81/examples/01_%E5%AE%8C%E6%95%B4%E5%AE%9A%E4%B9%89%E9%9C%80%E6%B1%82_v0.2.json)。旧v0.1的两个人工JSON样例仍是历史设计对照；新编译器不支持悄悄升级旧输入。输入必须明确提供srs、scope、三类控制内容、模板、授权、人机分工约束及additional_rules，缺项拒绝，不从安全底线补成“用户已要求”。输入不接受临床正文、SQL、执行代码、任意模块/路径选择、提交账号、审批或启用字段。

独立只读发行资产位于`05_系统代码/vetcontrols/data`：

| 资产 | 用途 |
| --- | --- |
| base_floor.json | SR01—10、CS01—06、模板、人机分工及质量目标底线 |
| permission_floor.json | 三角色、20权限键、29固定模式、35逻辑投影、208字段的目录 |
| registry.json | 10检查器、11阶段、87事实的机器元数据；未来可信服务提供者契约 |
| demand.schema.json | JSON Schema 2020-12结构、常量及数值边界，独立于被校验输入 |

这些资产是受信任程序发行部分，不允许请求方上传替换。若本地程序和发行资产一同被改写，摘要不能证明原始发行真实性；后续发布与运行审批仍要绑定可信版本。编译器不联网加载schema，不执行输入中的表达式或模块名。实现采用jsonschema 4.25.1，官方API见[版本文档](https://github.com/python-jsonschema/jsonschema/blob/v4.25.1/docs/errors.rst)。schema检查后仍执行条件类型、引用图、重复编号及范围等语义检查。

## 2. 不可削弱与可扩展部分

SR编号、checker、phases、failure_class、may_weaken及来源必须与底线一致，不能用同编号替换实现、删除阶段或添加when使必查项失效。CS逐项比对机器义务，不能仅保留编号而改成允许SQL拼接等相反含义。授权首版整体等值比对：角色、行谓词、投影、固定模式和拒绝归店不准增删或放宽。此严格性是首版编译实现范围，不表示所有将来合理的收紧提案均已支持。

质量仍是`targets_not_results`：覆盖率下界≥80%且≤100%；代码行范围在3200—4800内且下界≤上界；门店/宠物/病历数据量下界分别5/6000/20000；负载并发≥360、时长≥600秒、吞吐≥800/分钟、P95正数且≤280ms、授权请求失败上限0。扩展代价上限≤1文件/1模块/1人天。更小的最低支持屏幕可接受，更高的最低支持屏幕会缩小支持范围，因此拒绝。其他测量口径、浏览器、必需证据等义务保持原值。静态定义通过不产生覆盖率、行数、负载或浏览器实测结果。

模板保留诊断必填、用药三项齐全、用药只追加及更正关联、原版本解释、建议来源、人工作出采纳及其理由等底线；不采纳理由仍可空。首版仅允许新增医生可见、可选、`x_`前缀且类型为text/integer/boolean的临床字段定义。逻辑投影中的semantic_group有边界描述，不能当作任意实体序列化许可；内层实体运行序列化尚未实现。

额外规则仅能引用已登记checker及其阶段，来源必须已登记；条件只允许present/eq/in/all/any、已登记且阶段可用的事实与严格同类型字面量，不转换字符串数字、布尔和整数。after_commit_only事实不得作为写前条件。规则编号唯一，依赖须闭合且无环；额外条件规则与无条件底线调度分别输出。编译器检查定义，不执行这些运行条件或临床检查器。

## 3. 阶段与提交后结果

v0.2显式将不采纳操作映射为decision_change，将接待写入映射为reception_change；SR04增加decision_change，SR09增加decision_change/reception_change。实现审查再将SR06的审计计划调度及设施/计划/同事务计划事实扩到这两阶段，提交后atomic观察也覆盖；这是既定响应前必需审计和留存的可靠性实现选择，不声称NFR04原文逐字要求接待/不采纳同事务。SR06本身仍是审计/导出设施失败类别；接待/不采纳不加载SR02/03，不产生仅因登记失败的临床命中。此技术映射不增加业务权限。旧样例和原工程提案不动，新输入缺少这些阶段会被拒绝。

SR06中的同事务审计是提交计划；真正提交/审计持久化结果由未来可信提交观察者给出，不能把“审计已经成功”当作写前已知事实。registry保留提交后事实且禁止条件选择。临床告警只来自实际执行后确认的临床护栏命中，不能把schema、授权、设施缺失、不采纳或接待失败统一变成临床告警。

工程代理04提案保存完整接入设想；当前机器registry只纳入本批必需的无歧义技术字段，另登记principal.role及operation.mode，由未来服务端身份与入口提供。提案里的phase_contracts/after_commit_obligations尚未成为运行处理程序，不能据本批宣称其已集成。

## 4. 规范化、候选和复核

所有对象按键排序；本格式列表按集合规范化排序，保留重复项以便拒绝重复，屏幕宽高二元组保序。不修改调用方输入。规范化JSON采用UTF-8、无多余空格、键排序，SHA256以大写十六进制输出。输入摘要覆盖规范化输入；内容摘要覆盖payload；payload包含需求、底线调度、附加条件规则和发行底线/目录/schema的组合摘要。调度是静态计划，尚不是实际执行记录。

候选固定为draft_unsubmitted，submitted_actor/approval/activation均null，runtime_handlers为not_integrated、quality_results为not_measured。verify重新以独立底线编译payload.demand，再比较整个候选，不能只相信重算的摘要或自报active标志。通过只证明与当前发行契约一致，不证明作者身份、管理审批或已启用。

## 5. 失败、资源与命令行

错误只输出code、字段路径和固定说明，不转发第三方异常中可能含输入原值的message。定义输入≤1MiB、树深≤64、节点≤30000；条件深≤16、节点≤1000、每组≤256项、字符串条件字面量≤256字符；额外规则≤128、额外字段≤64。展开的候选也须满足相同树及文件字节边界，超出则以CANDIDATE_LIMIT拒绝，不产出自己无法复核的候选；候选文件用紧凑UTF-8和LF换行保存。这些是定义编译技术边界，与病历导出数量、正式临床负载无关。拒绝重复JSON键、非有限数、非UTF-8、未知字段、循环API对象及未知语法。

CLI的compile/verify均要求一个不存在的结果目录；不覆盖旧证据。compile成功输出candidate.json和report.json；失败只输出report.json，退出2；verify输出复核报告，不另发候选。文件不可读、输入过大或输出不可写均失败，写候选先写.pending再改名。报告包含原文件摘要（成功读到完整且未超限时），不包含输入正文。SHA256不是数字签名。
