# VetRules系统设计报告（验收候选稿）

> 2026-10-25；以[需规v1.0](../03_%E9%9C%80%E6%B1%82%E8%A7%84%E6%A0%BC%E8%AF%B4%E6%98%8E%E4%B9%A6.md)为业务基线，汇总本目录设计与当前实现。`architecture.md`保留早期候选比较；**当前交付实现**为Django/DRF＋MySQL＋RabbitMQ，同源原生HTML/CSS/JS工作台。设计依据与实测结论分别见本报告和[测试报告](../06_%E6%B5%8B%E8%AF%95%E4%B8%8E%E5%AE%9E%E6%B5%8B%E6%8A%A5%E5%91%8A.md)。

## 1. 目标、范围与架构取舍

T22的核心是先将病历/处方约束转成可校验的控制包，再让服务端按角色、门店和本次接待/接诊归属执行授权、护栏和审计。运行角色仅前台、医生、管理；宠物主人没有登录端。前台处理其负责接待的本次资料，医生处理其在本店负责接诊的病历及告警，管理只处理本店规则/模板、人机分工、汇总与脱敏审计，不读取诊断、处方和建议正文。具体字段边界见[权限矩阵](02_%E6%9D%83%E9%99%90%E7%9F%A9%E9%98%B5%E4%B8%8E%E5%AD%97%E6%AE%B5%E6%8A%95%E5%BD%B1.md)。

[架构候选比较](architecture.md)曾比较FastAPI/SQLAlchemy/PostgreSQL与Django/DRF/MySQL，用户选择后者优先预研：身份、ORM与迁移集中，便于把业务约束、事务和运行证据连到同一单体。实际实现使用Django/DRF、MySQL和RabbitMQ；前端为原生同源静态工作台，**没有采用早期候选中的Vue**。当前复现以Windows上的单机分层单体为准，Web、后台告警进程共用代码库，数据库和消息队列不对浏览器暴露。候选的Caddy/4×8入口实验仅是预研，不是最终已验收部署。

| 层/模块 | 当前职责 | 核心边界 |
| --- | --- | --- |
| 同源工作台与HTTP接口 | 三角色页面、表单、会话/CSRF与JSON/CSV交互 | 页面隐藏不构成授权；所有受保护请求由服务端复核 |
| 身份/治理 | 可信账号、角色/门店上下文；规则/模板候选、检查、审批与手动启用 | 不以Django staff/superuser代替业务角色；审批绑定内容版本 |
| 接诊/临床 | 固定接待与医生归属、诊疗版本、用药只追加、建议决定 | 同一提交的授权、当前模板、状态和版本核对；原项不覆盖 |
| 护栏/告警/队列 | 按生效规则判定，命中持久化告警与待发，再由后台投递/消费 | MQ消息只传引用；送达与医生处理分开；重投去重 |
| 审计/导出/管理投影 | 读取与导出访问审计、三类受限CSV、本店脱敏汇总 | 完整生成和必要审计成功后才交付字节；管理无临床正文 |

## 2. 控制文件与版本治理

[控制文件格式与生成](01_%E6%8E%A7%E5%88%B6%E6%96%87%E4%BB%B6%E6%A0%BC%E5%BC%8F%E4%B8%8E%E7%94%9F%E6%88%90%E6%A0%A1%E9%AA%8C%E8%AE%BE%E8%AE%A1.md)和[机器契约](08_%E6%8E%A7%E5%88%B6%E5%8C%85%E6%9C%BA%E5%99%A8%E5%A5%91%E7%BA%A6%E4%B8%8E%E9%9D%99%E6%80%81%E7%BC%96%E8%AF%91.md)规定需求输入含安全红线、编码规范、质量门禁、字段/模板、授权及分工约束。编译器按发行的Schema、底线和事实登记表做结构与语义校验；缺项、冲突、未知检查器或越过底线失败。编译成功只得未提交候选，不自动成为门店生效规则。管理账号在系统内提交、人工检查/审批并手动启用本店版本；病历引用其当时模板，旧病历仍按原版本解释。提交文件与各自用途见[AI可执行规格说明](21_AI%E5%8F%AF%E6%89%A7%E8%A1%8C%E8%A7%84%E6%A0%BC%E6%8F%90%E4%BA%A4%E7%B4%A2%E5%BC%95%E4%B8%8E%E8%AF%B4%E6%98%8E.md)，不要把设计样例当已生效控制包。

## 3. 核心数据与关系

[数据与接口详细设计](03_%E6%95%B0%E6%8D%AE%E4%B8%8E%E6%8E%A5%E5%8F%A3%E8%AE%BE%E8%AE%A1.md)保留类图、键、索引、接口和错误。关键关系在实现中为：一个接诊固定门店、接待账号与接诊医生；正式病历按接诊建立多个不可覆盖的修订版本；用药原项与更正项以同病历引用相连；建议只产生一项终态决定；规则命中对应告警及持久待发事件；审计记录动作、结果、操作者与受控目标关联。普通资料更正和误建保留历史，不通过删除记录“修复”。管理汇总从脱敏投影获取计数，不先读临床全文后删字段。

外部引用使用随机标识；身份和门店从服务端会话与持久记录获得，不信客户端自报。操作幂等键绑定账号、权限、目标、模式、内容摘要和期望版本，同键换内容拒绝。对外临床JSON与CSV都按当前授权、原模板字段及更正链产生，不能让关联子对象扩大医生可见范围。实际请求/响应字段及CSRF说明见[前端接口交接](13_%E5%89%8D%E7%AB%AF%E5%AF%B9%E6%8E%A5%E4%B8%8E%E6%8E%A5%E5%8F%A3%E4%BA%A4%E6%8E%A5.md)、[建议](14_%E6%BC%94%E7%A4%BA%E5%BB%BA%E8%AE%AE%E4%B8%8E%E4%BA%BA%E5%B7%A5%E5%86%B3%E5%AE%9A%E6%8E%A5%E5%8F%A3.md)、[管理汇总](17_%E7%AE%A1%E7%90%86%E8%84%B1%E6%95%8F%E6%B1%87%E6%80%BB%E6%8E%A5%E5%8F%A3.md)、[分工](19_%E4%BA%BA%E6%9C%BA%E5%88%86%E5%B7%A5%E7%99%BB%E8%AE%B0%E4%B8%8E%E5%A4%8D%E6%A0%B8%E6%8E%A5%E5%8F%A3.md)、[导出](20_%E5%8F%97%E9%99%90%E5%AE%8C%E6%95%B4CSV%E5%AF%BC%E5%87%BA%E6%8E%A5%E5%8F%A3.md)。

## 4. 关键时序与异常处理

[详细时序设计](04_%E5%85%B3%E9%94%AE%E6%B5%81%E7%A8%8B%E4%B8%8E%E6%97%B6%E5%BA%8F%E8%AE%BE%E8%AE%A1.md)含授权读取、临床写入、告警恢复和治理启用图及伪代码。下面列出提交时必须能解释的顺序：

1. **授权读取**：取得当前可信身份→按目标门店/归属/权限键确定数据行与字段→读取授权投影并提交必需访问审计→返回数据；拒绝路径记录脱敏原因，跨店拒绝事件归请求账号所属店管理可查。
2. **临床提交**：授权与操作幂等核对→事务内固定生效策略、锁目标并核版本→按模板、状态、只追加和护栏校验→通过时提交业务版本与审计；命中时不保存临床变更，但持久保存拒绝、命中、告警和outbox；持久化未确认时不能声称告警已记。
3. **队列恢复**：告警与outbox先在数据库持久化→后台有界领取/发布确认→消费收据落库后ack；同一消息重投不新增告警，医生另行处理。完整协议见[队列设计](16_%E5%91%8A%E8%AD%A6%E9%98%9F%E5%88%97%E6%8A%95%E9%80%92%E4%B8%8E%E6%81%A2%E5%A4%8D.md)。
4. **治理启用**：候选校验与提交→真实管理账号核对应审批的内容版本→审批→手动切换本店生效指针。新提交与既有病历保持版本边界，不因启用新模板覆盖旧病历。

![图3 医生提交病历时的判定顺序](23_%E6%8A%A5%E5%91%8A%E6%8F%92%E5%9B%BE/03_%E4%B8%B4%E5%BA%8A%E6%8F%90%E4%BA%A4%E6%97%B6%E5%BA%8F.png)

图3抽取[完整临床写入与队列时序](04_%E5%85%B3%E9%94%AE%E6%B5%81%E7%A8%8B%E4%B8%8E%E6%97%B6%E5%BA%8F%E8%AE%BE%E8%AE%A1.md)的共同不变量；医生提交成功与护栏阻断是两条不同持久化结果，后台只在告警及待发记录持久化后处理消息。

| 临床提交伪代码步骤 | 必须保持的行为 |
| --- | --- |
| `actor = trusted_session(request)`；核对操作键 | 账号、门店、接诊归属与状态由服务端判定；同键换内容拒绝。 |
| 事务中锁定接诊并读取当前模板/策略、期望版本 | 版本冲突不能覆盖旧修订；更正只新增关联项。 |
| `verdict = guard.validate(candidate, active_policy)` | 通过才保存新临床版本与同事务审计；阻断则保存拒绝、命中、告警及outbox，不写入违规临床正文。 |
| 提交后后台从outbox发布引用并记录消费收据 | 同次重投不新增告警；医生处理告警是另一个受权操作。 |

## 5. 质量与可追踪的实测结果

[需求到设计矩阵](05_%E9%9C%80%E6%B1%82%E5%88%B0%E8%AE%BE%E8%AE%A1%E8%BF%BD%E8%B8%AA%E7%9F%A9%E9%98%B5.md)把FR/NFR/AC映射到设计对象；真实执行结论以[测试报告](../06_%E6%B5%8B%E8%AF%95%E4%B8%8E%E5%AE%9E%E6%B5%8B%E6%8A%A5%E5%91%8A.md)及[最终源码复验](../10_%E9%AA%8C%E6%94%B6%E8%AF%81%E6%8D%AE/21_%E6%9C%80%E7%BB%88%E6%95%B4%E4%BD%93%E9%AA%8C%E6%94%B6%E4%B8%8E%E6%8F%90%E4%BA%A4%E6%95%B4%E7%90%86/02_%E6%9C%80%E7%BB%88%E6%BA%90%E7%A0%81%E5%89%8D%E5%90%8E%E7%AB%AF%E5%A4%8D%E9%AA%8C.md)为准。当前完整MySQL/RabbitMQ回归198项通过、0失败、0跳过，生产Python语句覆盖率89%。角色/越权、事务、队列停复、模板旧版、导出与脱敏审计均有相应测试及阶段证据。五店/6000宠物/2万病历的课程活跃会话正式负载持续600秒、完成10774次请求、零失败，七类完整响应P95为65.1—138.4ms；实际在途P95为3、峰值12。该成绩仅对应[活跃会话协议](../10_%E9%AA%8C%E6%94%B6%E8%AF%81%E6%8D%AE/19_%E5%90%8E%E7%AB%AF%E7%BB%BC%E5%90%88%E9%AA%8C%E6%94%B6/24_AC06%E8%AF%BE%E7%A8%8B%E5%8F%A3%E5%BE%84v1.1%E5%AE%8C%E6%95%B4%E9%AA%8C%E6%94%B6.md)，先前持续360请求在途试验作为不同强压力边界保留原始记录。

本报告的当前实现以本节、[代码说明](../../backend/README.md)和[09运行说明](../09_%E8%BF%90%E8%A1%8C%E4%B8%8E%E6%8F%90%E4%BA%A4%E8%AF%B4%E6%98%8E.md)为准；早期候选中的Vue/Caddy用于比较，不代表当前产品组件。
