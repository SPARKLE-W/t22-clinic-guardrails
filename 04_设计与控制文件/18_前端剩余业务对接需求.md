## 2. 共同约束

| 项 | 约定 |
| --- | --- |
| 同源 | 所有接口与 `/app` 同源；Django session Cookie + CSRF；不引入 CORS 或跨域 Token |
| 身份 | 服务端从 session 取得账号、角色、门店；请求体/前端自报的 `actor_ref` 不能作为权限依据 |
| 范围 | 前台只本店本人接待；医生只本店本人负责接诊；管理只本店治理/汇总/脱敏；跨店拒绝并审计 |
| 管理边界 | 管理汇总/审计/导出均不得返回病历正文、宠物身份、命中值、建议原文、采纳理由或用药更正正文 |
| 时间 | 请求用带时区 ISO 8601；响应按原时区解析，前端显示本地时间；范围起点包含、终点不含 |
| 分页 | 列表默认 50，稳定排序，返回 `page`、`page_size`、`total`；导出不得只导出当前页 |
| 写入 | 需要幂等的写操作沿用 `Idempotency-Key`；同键不同内容按现有冲突语义拒绝 |
| 错误 | 现有 `{ok:false,error:{code}}`；流式导出在开始传字节前返回 JSON 错误，传字节后只能断开，不能改 HTTP 状态 |
| 审计 | 汇总读取、分工写/复核、每次导出尝试都要有可核对审计；审计失败不得先返回受保护内容 |
| 不伪造 | 前端不计算管理聚合、不拼 CSV 冒充服务端导出、不以隐藏按钮代替权限 |

## 3. 人机分工登记与复核

### 3.1 业务要求

- 管理按“工作项 + 阶段”登记计划分工，并登记有来源的实际执行信息；系统比较同维度，输出一致/待复核/不可比较。
- 实际执行证据只采信系统已记录、可定位的账号/角色、时间、结果、来源/事件引用；缺资料判“不可比较”，不判一致。
- 管理人工复核差异；自动比较不能替代复核，复核关联真实管理账号、时间、理由和适用版本。
- 不返回临床正文、建议原文、采纳理由或用药更正正文；引用不能打开正文。
- 工作项示例：内容生成、人工采纳、规则审批、告警处理；计划维度至少区分“内容生成方式 / 录入账号 / 人工决定主体”。

### 3.2 建议数据对象（需评审）

`work_division`：

| 字段 | 类型/说明 |
| --- | --- |
| `work_division_ref` | UUID，稳定引用 |
| `work_item` | 可识别的工作项，建议受控枚举或“枚举 + 说明” |
| `stage` | 阶段/环节，受控值 |
| `plan_version` | 计划版本，递增，不可覆盖 |
| `plan` | 维度/值；至少含 `content_generation`、`data_entry`、`human_decision` |
| `actual` | 实际执行证据：方式、账号/角色、时间、结果、`event_ref`/来源引用 |
| `comparison` | `consistent` / `pending_review` / `not_comparable`（建议值） |
| `comparison_basis` | 比较所用计划版本与实际记录版本/事件引用 |
| `review` | 复核结论、理由、管理账号、时间、适用版本 |
| `created_at` / `updated_at` | 服务端时间 |

- 对比结果绑定版本；计划或实际变化后重新比较，旧结论保留。
- 同一工作项/阶段可以有多个历史版本；列表默认显示当前版本与最近复核状态。
- 实际执行证据可引用既有事件（采纳、审批、告警处理等）；不要为前端另造“人工/AI”登录角色。

### 3.3 建议接口

| 方法与路径（建议） | 用途 | 关键约束 |
| --- | --- | --- |
| `GET /api/management/work-divisions?stage=&status=&page=` | 本店列表/筛选 | 只返回脱敏元数据；稳定排序；`status` 为 comparison/review 状态 |
| `GET /api/management/work-divisions/{ref}` | 详情 + 版本/复核历史 | 只本店；引用不返回正文 |
| `POST /api/management/work-divisions` | 登记计划/实际执行或更新 | 管理权限；`Idempotency-Key`；版本冲突 409；写审计 |
| `POST /api/management/work-divisions/{ref}/reviews` | 人工复核 | 管理权限；绑定被复核版本；理由必填；写审计；旧结论保留 |

建议错误码沿用现有：`PERMISSION_DENIED` 403、`TARGET_UNAVAILABLE` 403、`INPUT_FIELDS_INVALID` 422、`STATE_OR_VERSION_CONFLICT` 409、`PERSISTENCE_UNAVAILABLE` 503。具体码表需后端冻结。

### 3.4 前端页面与状态

- 管理导航新增「人机分工」；列表显示工作项、阶段、计划版本、比较状态、最近复核、更新时间。
- 新建/更新弹窗：工作项、阶段、计划维度、实际证据引用/说明、理由；保存后显示比较结果，不直接把“待复核”显示成一致。
- 复核弹窗：结论（一致/需修正/不可比较）、理由、适用版本；提交后保留历史。
- 空态、403、409、503、加载骨架与焦点管理沿用现有模式。
- 前端不提供“AI 自动审批”按钮；不把 AI 建议源当登录角色。

### 3.5 后端工作量与验收

- 模型/迁移、服务、权限、版本/并发、审计、比较逻辑；如引用既有事件，需要稳定的 `event_ref` 关联。
- 测试：跨店拒绝、无工作项/阶段、缺证据 → 不可比较、计划变更后新版本、复核后旧差异保留、重复请求、审计失败。
- 前端验收：列表/详情/复核、状态不混淆、管理不看到正文、键盘/空态/错误态。

## 4. 管理汇总（后端已交付，前端接入）

### 4.1 已交付契约

后端已交付 `GET /api/reports/store-summary`，权限 `report.store_summary.read`，仅当前有效管理账号；服务端从账号决定门店。详细契约见[17_管理脱敏汇总接口](17_管理脱敏汇总接口.md)，机器契约见[05汇总OpenAPI](控制文件/05_管理汇总_openapi_v1.json)。

- 可选查询：`time_range`（URL 编码 JSON，含带时区 `from`/`to`，起点包含、终点不含；省略为全部时间）与 `group_by`（`rule`/`handling_state`，默认 `rule`）。
- 顶层字段固定为 `time_range`、`encounter_created_count`、`error_marked_count`、`hit_count`、`alert_count`、`unhandled_count`、`grouped_counts`。
- `grouped_counts.items` 按规则为 `rule_ref`、`hit_count`、`alert_count`、`unhandled_count`；按状态为 `handling_state`、`alert_count`。
- 不返回宠物/接诊/病历/事件标识、账号、主诉、诊断、处方、命中值、AI 建议或自由文本理由。
- 无分页/下钻；未知字段、重复参数、非法时间或分组返回 422；401/403/405/422/503 沿用现有错误体。
- 口径：接诊数含误建与重建；误建数是读取时已标记的集合；命中/告警按各自事实时间；未处理/已处理是读取时状态，不是期间处理次数。

### 4.2 前端页面

- 管理导航新增「本店汇总」；时间范围提供“全部 / 今日 / 近 7 天 / 自定义”中接口支持的范围，分组切换 `rule` / `handling_state`。
- 顶部显示接诊数、误建数、命中数、告警数、未处理数；下方按规则或状态显示计数表；标注“统计截至”和服务端时间。
- 空结果显示 0 与空态，不显示错误；422/403/503 按现有错误组件展示；加载用列表/统计骨架。
- 所有数值直接来自 `store-summary`，前端不做二次聚合；不提供病例下钻，不调用医生接口补数据，不用审计 100 条估算总额。
- 汇总读取本身写审计；页面不把读取成功伪装成告警处理或导出完成。

### 4.3 验收

- 前台/医生/跨店拒绝；管理只本店；`time_range` 半开区间；空结果返回零；误建/重建计数符合契约；`group_by` 两种视图正确；未知字段/重复参数 422；审计 503 不返回部分计数。
- 前端断言直接使用固定响应字段，不自行相加 `grouped_counts` 覆盖顶层总数；切换时间/分组重置分页与滚动位置。
- 正式数据量/性能按第十六阶段证据与后续验收，不在页面开发中伪造。

## 5. 三类 CSV 导出

### 5.1 共同要求（C-05/C-08）

- 三类导出分开授权、分接口或至少分 scope；不能靠前端隐藏字段。
- UTF-8 CSV；完整所选授权范围，不静默截断，不只导当前列表页；无结果明确为空，不混作失败。
- 医生病历导出保留版本与更正链、模板版本、正式采纳内容、用药原项/关联更正；不混入未采纳建议。
- 管理汇总导出只按规则/处理状态计数，不带病例级身份、正文、命中值或自由文本原因。
- 每次导出写访问/导出审计；审计持久化成功后才开始传文件；失败不返回临床字节。
- 区分“服务端已就绪”“客户端完整接收”“中断/未完整接收”；用户保存到磁盘是浏览器行为，服务端不能冒充已确认。
- 计时从请求到完整文件响应，包含生成和审计；正式性能另做。

### 5.2 导出一：医生病历 CSV

**路径建议**：`POST /api/exports/clinical-records`

请求：

```json
{
  "encounter_refs": ["<UUID>", "<UUID>"],
  "from": "2026-10-01T00:00:00+08:00",
  "to": "2026-11-01T00:00:00+08:00",
  "purpose": "复诊对照",
  "format": "csv"
}
```

- `encounter_refs` 与 `from/to` 二选一；不得混用未定义字段。
- `purpose` 必填（UC-08）；用途原文只存审计，不写临床正文。
- 响应：`text/csv; charset=utf-8`，`Content-Disposition`，`X-Export-Ref`，`Content-Length`。
- 建议长表（一行一个可解释事实），列建议：

`encounter_ref, record_ref, version, row_type, parent_ref, template_ref, template_version, field, value, actor_ref, actor_role, occurred_at, reason, error_mark`

`row_type` 至少覆盖：接诊、诊断/检查、用药原项、用药关联更正、正式采纳、版本/更正关系。具体列需按 C-08 与模板定义冻结；不要在未确认前列死。

### 5.3 导出二：医生告警命中明细 CSV

**路径建议**：`POST /api/exports/alert-hits`

请求：

```json
{
  "from": "2026-10-01T00:00:00+08:00",
  "to": "2026-11-01T00:00:00+08:00",
  "rule_refs": ["SR-02", "SR-03"],
  "handling_states": ["handled", "unhandled"],
  "purpose": "复核告警处理"
}
```

- 只限当前医生本店负责接诊；不得借管理账号导出明细。
- 建议列：`alert_ref, event_ref, rule_ref, rule_label, hit_field, record_ref, handling_state, handler_ref, handled_at, handling_result, created_at`。
- **命中值是否导出未冻结**：C-05 只明确“命中字段”，管理明确不含命中值；医生明细是否含值需产品确认。默认 **不返回原文命中值**，只返回字段名与规则/处理元数据；若确认可返回，需单独字段白名单和脱敏审计。
- 不改变告警处理状态；重复导出是新的访问审计。

### 5.4 导出三：管理告警汇总 CSV

**路径建议**：`POST /api/exports/alert-summary`

请求：

```json
{
  "from": "2026-10-01T00:00:00+08:00",
  "to": "2026-11-01T00:00:00+08:00",
  "rule_refs": [],
  "handling_states": ["handled", "unhandled"],
  "purpose": "月度治理复核"
}
```

- 管理只本店；聚合，不带病例级身份、命中值、正文或自由文本原因。
- 建议列：`rule_ref, rule_label, handling_state, alert_count, hit_count, generated_at`。
- `alert_count` 与 `hit_count` 分列，避免把“独立命中项”和“告警条数”混成一个数；具体口径按 §7.6。
- 不提供下钻链接；不返回 `record_ref`/`alert_ref`。

### 5.5 导出审计

建议新增/复用审计动作，至少记录：

- `export_ref`、导出类型、真实操作账号/角色、门店、时间。
- 查询条件（范围、规则、状态、是否含用途）、用途（仅 UC-08 必需）、结果（ready/complete/incomplete/refused/failed）、记录数/行数/字节数、错误码。
- 文件生成/审计失败：不返回 CSV；审计写入与生成的成功顺序必须可验证。
- 客户端中断/网络断：服务端记录“已就绪/可能未完整接收”的真实状态；不能凭客户端另存为判断成功。

### 5.6 前端下载状态

- 弹窗收集范围/用途（医生病历必填），提交后显示“生成中”。
- 成功后用 Blob 下载；以 `Content-Length` 与实际字节数比较判断“完整接收”；不匹配或网络中断显示“未完整接收/结果待核对”，不显示“导出成功”。
- 403/422/503 在开始传字节前按 JSON 错误展示；已开始传字节后中断，保留导出引用供核对。
- 前端不拼接 CSV、不截断列表、不把当前页当全量。

### 5.7 验收

- 角色/跨店/前台拒绝；用途必填仅 UC-08；管理汇总不含身份/命中值/正文；医生明细不含管理汇总权限。
- CSV 可解析、列含义、版本/更正链、空结果、完整范围、多行更正、误建标识。
- 审计失败不返回字节；断连/重试/重新下载的审计；P95 从请求到完整文件。
- 在真实规模下核对记录数/行数/字节数；不只测受理响应。

## 6. 告警投递状态（条件项）

需求要求业务处理状态与消息投递状态分别可查。现状：`alert_delivery --inspect` 是内部运维命令，没有医院 Web 查询接口。

需要产品先决定：

1. **只保留运维命令**：在交付说明中明确“投递状态不进入医院 Web 界面”，前端不做。
2. **进入只读界面**：建议 `GET /api/clinical/alerts/{alert_id}/delivery`（医生本人）或 `GET /api/management/alert-delivery?...`（管理本店聚合），只返回 `event_ref`、投递状态、尝试次数、最后尝试时间、标准错误码；不返回告警正文/命中值。
   - 若管理可见，只按本店聚合，不返回病例级明细。
   - 若医生可见，只限本人负责告警，且不改变业务处理状态。

未冻结前，前端不展示投递状态，也不从 `handled/unhandled` 推断投递成功。

## 7. 可选：审计检索扩展

当前 `/api/audit` 只返回最近 100 条，支持 `record_ref`、`operator_ref`。若课程验收要求按动作/结果/时间检索或超过 100 条，需要后端增加分页/筛选；前端再加筛选和页码。

这不是当前前端页面可以自行解决的：前端只有已返回的 100 条，不能据此声称全量审计。是否扩展按 C-06/验收口径决定，建议不列入首版 P0。
