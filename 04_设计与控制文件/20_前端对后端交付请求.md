## 2. F-04 需要后端交付什么

### 2.1 共同约定（请求确认）

- 同源、Django session + CSRF；服务端从当前账号取角色/门店，不接受前端自报身份。
- 三类导出分别授权，不能靠前端隐藏字段；范围必须在服务端完整执行，**不得只导当前页，不得静默截断**。
- 每次尝试写导出审计；**审计持久化成功后才开始传 CSV 字节**；审计失败返回 503，不先传临床数据。
- UTF-8 CSV；空结果明确为空，不混作失败；具体是否加 BOM、文件名规则请后端给出并冻结。
- 区分：服务端已生成/就绪、客户端完整接收、中断/未完整接收；服务端不能冒充“用户已保存到磁盘”。
- 错误在开始传字节前用现有 `{"ok":false,"error":{"code":...}}` JSON；开始后只能断开，不能改 HTTP 状态。
- 建议响应头：`Content-Type: text/csv; charset=utf-8`、`Content-Disposition`、`X-Export-Ref`、`Content-Length`。
- 记录数/行数/字节数可回传（如 `X-Export-Rows`、`X-Export-Bytes`），便于前端核对完整接收。

### 2.2 三个端点（建议路径，请后端确认/改名）

| 方法/路径 | 角色/范围 | 请求（建议） |
| --- | --- | --- |
| `POST /api/exports/clinical-records` | 医生，本店本人负责接诊 | `encounter_refs[]` 或 `from/to` 二选一；`purpose` 必填；`format: "csv"` |
| `POST /api/exports/alert-hits` | 医生，本店本人负责接诊 | `from/to`；`rule_refs[]` 可选；`handling_states[]` 可选；`purpose` 必填 |
| `POST /api/exports/alert-summary` | 管理，本店 | `from/to`；`rule_refs[]` 可选；`handling_states[]` 可选；`purpose` 必填 |

- 前台不开放导出；管理不能借导出读病历明细；医生不能导管理汇总。
- 时间建议带时区 ISO 8601，起点包含、终点不含；请明确最大范围。
- 导出请求是否需要 `Idempotency-Key`、重复下载是否每次新建审计，请冻结。

### 2.3 CSV 列（提案，需后端/产品冻结）

**医生病历（长表，一行一个可解释事实）：**

`encounter_ref, record_ref, version, row_type, parent_ref, template_ref, template_version, field, value, actor_ref, actor_role, occurred_at, reason, error_mark`

`row_type` 至少覆盖：接诊、诊断/检查、用药原项、用药关联更正、正式采纳、版本/更正关系。保留版本与更正链、模板版本、正式采纳内容；不混入未采纳建议。

**医生告警命中明细：**

`alert_ref, event_ref, rule_ref, rule_label, hit_field, record_ref, handling_state, handler_ref, handled_at, handling_result, created_at`

- 只限本人负责接诊；不改变告警处理状态。
- **命中值是否导出未冻结**：C-05 只明确“命中字段”，管理明确不含命中值；医生明细是否含值请产品确认。默认不返回原文命中值。

**管理告警汇总：**

`rule_ref, rule_label, handling_state, alert_count, hit_count, generated_at`

- 只本店、聚合；不带病例身份、命中值、正文或自由文本原因。
- `alert_count` 与 `hit_count` 分列，避免把独立命中项和告警条数混成一个数。

### 2.4 导出审计

请确认/补齐每条导出审计的字段：

- `export_ref`、导出类型、真实操作账号/角色、门店、时间；
- 查询条件（范围、规则、状态）、用途（仅 UC-08 必需）；
- 结果（ready/complete/incomplete/refused/failed）、记录数/行数/字节数、错误码。

审计失败不得先返回 CSV；客户端中断/网络断时服务端记录真实状态，不能凭浏览器另存为判断成功。

### 2.5 联调夹具与 Definition of Ready

请随 F-04 提供：

1. 真实路由或至少 OpenAPI（三个端点、请求/响应、错误码、示例）。
2. 一份可登录的合成门店数据：至少两条接诊、版本/更正、用药原项/关联更正、告警、已/未处理各一条。
3. 权限反例：前台、跨店医生、管理调医生明细、医生调管理汇总。
4. 空结果、超过一页/超过当前列表、审计失败、客户端中断的测试方式。
5. CSV 列顺序/含义/空值/UTF-8 BOM/文件名冻结说明。

## 3. 告警投递状态

需求要求业务处理状态和消息投递状态分别可查；当前只有内部 `alert_delivery --inspect`。请产品/后端明确：

- A. 保留运维命令，不进入医院 Web（请写进交付说明）；或
- B. 提供只读接口，如 `GET /api/clinical/alerts/{alert_id}/delivery`（医生本人）或管理本店聚合；只返回 `event_ref`、投递状态、尝试次数、最后尝试时间、标准错误码，不返回告警正文/命中值。

在冻结前，前端不展示投递状态，也不从 `handled/unhandled` 推断投递成功。

## 4. F-05 需要的联调条件

- 一个可控的真实 `GUARD_BLOCKED` 场景：例如合成接诊 + 合成诊断内容，客户端可提交但后端护栏拒绝；需给出输入与预期 `event_ref`，避免误写真实数据。
- 真实 503/断网/超时窗口（或明确接受用 CDP 故障注入作 UI 证据）。
- 实际 Edge 浏览器菜单 200% 的检查方式；如果只能以 2× device scale + 683 CSS 视口代替，请确认证据口径。
- E2E 所需的测试账号/门店/合成记录，以及登录后数据不会被其他批次清理的保证。
