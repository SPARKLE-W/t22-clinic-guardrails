# 280 ms 容量与架构可行性分析

> 2026-10-24；本文是对已冻结正式负载、当前源码与部署条件的**分析**，不是新一轮 AC-06 实测，不修改[《01_正式负载测量协议_v1.0》](01_正式负载测量协议_v1.0.md)，不改代码、权限、审计或导出契约。供后端开发复核容量假设与三处卡点；凡涉及“是否调整并发口径/导出契约”的结论，须由本人和老师确认，不能由本文自行生效。

## 0. 结论摘要

| 口径 | “360”指什么 | 需要的稳态吞吐 | 判断 |
| --- | --- | ---: | --- |
| A | 360 个并发用户，每次操作之间有 5—10 秒思考时间 | 约 35—70 次/秒 | **可达**；以部署、连接复用和导出边界为主，不需要换技术栈 |
| B | 360 个请求持续在途，无人工思考时间（已冻结） | 约 1,286 次/秒 | **当前单机同步架构不可达**；差约 47 倍 |

分层看：

- **数据与查询：不是瓶颈。** 5 店、约 6,000 只宠物、约 2 万份病历对 MySQL 是小表；已有 `(store, doctor, created_at)` 组合索引，单页 50 条。查询本身应在 10—40 ms 量级，不需要分库分表、NoSQL 或微服务。
- **应用逻辑：基本不是。** 分段诊断中 app 内 P95 约 87—210 ms，已低于 280 ms；主要延迟落在“应用开始前”，即入口排队、HTTP 接入与调度。
- **写与护栏：是，但属于并发架构。** 每次写对 `Account`、`PolicyHead`、`Encounter` 三处做 `SELECT ... FOR UPDATE`；`PolicyHead` 每个门店只有一行，等于**同一门店的写请求串行**。
- **导出：是，而且是最硬的契约层。** 4,000 份病历完整 HTTP 约 776 ms；其中 4,000 条审计目标插入单项约 0.594 s；冻结配比里 10% 的病历导出是 1,000—4,000 份，10% 已大于 5%，所以**该类 P95 必然落在大导出区间**。在“同步生成 + 先审计后返回 + 完整响应计时”的现行契约下，这不是“难”，是算术上不可能。
- **部署与入口：是。** 120 个 Waitress 线程少于 360 个在途请求；队列深度曾达 242；压测客户端、Waitress 与 MySQL 同机；`CONN_MAX_AGE = 0` 意味着每个请求新建连接，没有复用。

一句话：**不是“框架选错了”，是并发临界区、导出契约和部署容量三件事；数据量本身完全不是问题。**

## 1. 两种并发口径

### 1.1 A：360 个并发用户

这是通常的 Web 负载口径：360 个用户在线，每个用户完成一次操作后思考 5—10 秒再发下一次。按 Little 定律，稳态吞吐约为 `360 / (5—10 s)`，即 **35—70 次/秒**。在这个量级上，2 万份病历的查询、护栏校验和 1—20 份的小导出，280 ms 是正常的 Web 目标，不是高性能计算目标。

### 1.2 B：360 个请求持续在途

冻结协议选择的是更严的口径：没有思考时间，任意时刻都有 360 个请求已经发出、尚未收到完整响应。若这些请求都要在 280 ms 左右完成，则完成能力必须是：

`360 / 0.28 ≈ 1,285.7 次/秒`，约 77,000 次/分钟。

这不是“平均值”，而是稳态服务率；低于它，在途数就会继续上涨或时延继续变大。

### 1.3 800 次/分钟不能当作容量设计点

800 次/分钟约为 13.3 次/秒。若系统只做到这个吞吐、同时保持 360 个请求在途，平均在途时间就是 `360 / 13.3 ≈ 27 秒`，与 280 ms 相差约 96 倍。

800 次/分钟是题定的**下限**，1,286 次/秒当然也满足它；问题在于不能反过来拿 800/分钟去设计容量。**真正约束容量的是“360 在途 + 280 ms”，不是 800/分钟。** 这也是为什么必须先确认 360 的语义：如果老师指的是“360 个用户”，800/分钟是合理下限；如果指的是“360 个在途”，800/分钟几乎不构成约束，真正的门槛是 1,286 次/秒。

## 2. 容量算术

以下均为量级估算，用于判断数量级，不是新一轮实测；不能替代同协议复测。

| 项目 | 数值 | 说明 |
| --- | ---: | --- |
| B 口径目标完成能力 | 1,286 次/秒 | `360 / 0.28` |
| 120 线程的理论完成上限 | 429 次/秒 | `120 / 0.28`，假设每请求占满 280 ms |
| 120 线程、360 在途的平均时延下界 | 约 840 ms | `360 / 429`；即使数据库零耗时也绕不过 |
| 要在 280 ms 内完成时，单请求平均服务时间上限 | 约 93 ms | `0.28 × 120 / 360` |
| 第二轮正式实测吞吐 | 27.2 次/秒 | [第二轮](05_正式负载第二轮实测.md) |
| 与目标完成能力的差距 | 约 47 倍 | `1,286 / 27.2` |

**关键结论：** 120 个工作线程、360 个在途请求，意味着每个请求平均要排 3 个批次。若单请求服务时间是 280 ms，平均时延至少 840 ms；要把平均时延压到 280 ms，单请求平均服务时间必须不超过 93 ms。这是排队论下界，不是“再优化一条 SQL”能绕过的。

要同时满足 360 在途与 280 ms，至少需要 360 个真正并行的处理槽；留 30% 余量约需 500 个。500 个并发数据库连接已超过当前 MySQL 的 `max_connections = 151`，因此必须使用连接池/代理，或把应用层拆到多节点。**这已经是容量等级的变化，不是线程数微调。**

## 3. 分层诊断

### 3.1 数据与查询：不是瓶颈

- `Encounter` 已有 `(store, receptionist, created_at)` 与 `(store, doctor, created_at)` 两个组合索引，见 [`clinic/models.py`](../../05_系统代码/clinic/models.py#L30)。
- 列表读取按 `created_at, id` 排序，单页 50 条，先 `count()` 再切片，见 [`clinic/services.py`](../../05_系统代码/clinic/services.py#L280-L281)。
- 约 2 万份病历、6,000 只宠物、5 家门店，核心业务表在几十到几百 MB 量级，可全部驻留内存；单页查询的主要成本是几次索引查询加预取，不是全表扫描。
- 读取路径也会写审计：每次读取创建一条 `AuditEvent` 和若干 `AuditTarget`，见 [`clinic/services.py`](../../05_系统代码/clinic/services.py#L297-L298)。所以“查询”不是纯读，但在当前数据量下仍不是主要瓶颈；它的影响在 1,286 次/秒的审计写入量上才会显现。

**判断：** 数据层不需要分库分表、读写分离或 NoSQL；当前 12—34 秒的延迟不是数据量造成的。

### 3.2 应用逻辑：基本不是

- [性能定位报告](../06_B方案技术预研/11_性能定位与对照结果.md)的分段计时显示：app 内 P95 约 87—210 ms，已经低于 280 ms；而“应用开始前”的 P95 约 1.8—3.5 秒，dispatch 约 33—52 ms，应用结束后到完整接收约 8—16 ms。
- 这说明业务代码本身可以在 280 ms 内完成；主要时间花在进入应用之前的排队、HTTP 接入、调度和客户端/同机压测开销上。
- 另有一个小的固定开销：`protected` 装饰器先调用一次 `require()`，视图内部的服务又调用一次，见 [`governance/views.py`](../../05_系统代码/governance/views.py#L41) 与 [`clinic/services.py`](../../05_系统代码/clinic/services.py#L242)。这是两次账号查询，属于可低成本消除的重复，但不是主因。

**判断：** 不需要重写业务逻辑；需要解决的是“请求在进入业务逻辑之前排了多久”。

### 3.3 写与护栏：按门店串行

当前诊断写入的事务顺序是：

1. `Account` 行 `SELECT ... FOR UPDATE`，见 [`clinic/writes.py`](../../05_系统代码/clinic/writes.py#L34)；
2. `PolicyHead` 行 `SELECT ... FOR UPDATE`，见 [`clinic/writes.py`](../../05_系统代码/clinic/writes.py#L36)；
3. `Encounter` 行 `SELECT ... FOR UPDATE`，见 [`clinic/writes.py`](../../05_系统代码/clinic/writes.py#L37) 与 [`clinic/services.py`](../../05_系统代码/clinic/services.py#L64)；
4. 然后才做规则评估、`ClinicalCheck`/`GuardHit`/`Alert`/`AlertOutbox` 插入、审计、`Operation` 插入，见 [`clinic/writes.py`](../../05_系统代码/clinic/writes.py#L75-L101)。

`PolicyHead` 每个门店只有一行，因此**在 `PolicyHead` 临界区内，同一门店的所有写请求都在这同一行上串行**；同一账号再叠一层 `Account` 锁。5 个门店最多只有 5 个并发写事务。

按当前实现（护栏校验落在诊断写事务内），冻结配比中写入 20% + 护栏 15% 合计 35%，在 1,286 次/秒下约 450 次/秒；分摊到 5 个门店是 90 次/秒/店，要求单事务不超过约 11 ms。即使只算 20% 正式写入，也要求单事务不超过约 19 ms。当前事务包含多次插入、规则评估和审计，远不止这个量级。

这不是“谁写错了”：锁是为了保证同一门店策略版本一致、幂等和审计先行；但它的代价就是**写吞吐按门店数封顶**。在这种情况下，继续增加 Waitress 线程不会提高写吞吐，只会让更多线程排队等同一行锁。

### 3.4 导出：现行契约下算术不可能

当前导出实现：

- 整个生成过程包在 `transaction.atomic()` 里，见 [`clinic/exports.py`](../../05_系统代码/clinic/exports.py#L79)；
- 先取记录并 `select_related`/`prefetch_related`，再在 Python 里拼 CSV，见 [`clinic/exports.py`](../../05_系统代码/clinic/exports.py#L103-L105) 与 [`clinic/exports.py`](../../05_系统代码/clinic/exports.py#L133)；
- 创建 `ExportRequest`、写一条审计、再为每个目标插入 `AuditTarget`，见 [`clinic/exports.py`](../../05_系统代码/clinic/exports.py#L134-L139)；
- 最后对完整 body 计算 SHA-256 并设置长度，见 [`clinic/exports.py`](../../05_系统代码/clinic/exports.py#L72-L74)。

证据：

- 4,000 份病历完整 HTTP：约 3.09 MB、12,296 行、**776 ms**，见[性能定位报告](../06_B方案技术预研/11_性能定位与对照结果.md)。
- 单次 SQL 诊断：4,000 行、2,750,980 字节、16 条 SQL、总约 **1.7 s**，SQL 合计约 0.86 s；其中 **4,000 个审计目标关联的批量插入约 0.594 s**，见[单次大范围导出 SQL 诊断](09_单次大范围导出SQL诊断.md)。

关键算术：

- 冻结配比中病历导出有 **10%** 为 1,000—4,000 份（见[280ms 评估](14_280ms门槛与代码规模口径评估.md) §1）。
- 10% 已经大于 5%，所以**病历导出这一类的 P95 必然落在 1,000—4,000 份的大导出区间**，不可能由 90% 的小导出把 P95 拉回 280 ms 以内。
- 而大导出的审计目标插入单项就是 0.594 s，已经是 280 ms 的 2 倍多；这还没算 CSV 生成、SHA-256、事务和网络。

因此：**病历导出类 P95 ≤ 280 ms，在现行“同步生成 + 先审计后返回 + 完整响应计时”的契约下不是难度问题，是算术上不可能。** 加机器、换框架、加线程都救不了；只能改契约（异步导出/对象存储/范围上限）或经批准调整配比与统计口径。

再按 1,286 次/秒做一个上限估算：若 20% 都按病历导出计，约 257 次/秒，其中 10% 大导出约 25.7 次/秒；每次 4,000 个审计目标，就是约 **10.3 万个审计目标/秒**。单次 4,000 条插入已经要 0.594 s，这个量级不可能在单机上持续。

### 3.5 部署与入口：容量不足

- Waitress 配置 120 线程；第二轮日志有 **25,135 条**排队告警，记录最大队列深度 **242**，见[第二轮](05_正式负载第二轮实测.md)。
- MySQL `max_connections = 151`，见[280ms 评估](14_280ms门槛与代码规模口径评估.md) §1。
- 正式压测把 360 个客户端线程、Waitress 和 MySQL 放在**同一台 Windows 机器**上；客户端 CPU 与服务器争抢，会放大“应用开始前”的时延。
- `DATABASES` 设置 `CONN_MAX_AGE = 0`，见 [`vetapp/settings.py`](../../05_系统代码/vetapp/settings.py#L18)：每个请求结束关闭连接，下一个请求重新握手，没有连接复用。

这些都属于部署与容量问题，不是业务代码问题。尤其是同机压测这一条：在换独立压测机之前，不能把所有 12—34 秒都归因给应用或数据库。

## 4. 架构判断

| 层面 | 是否是问题 | 理由 |
| --- | --- | --- |
| 技术选型 | **不是** | Django/DRF + MySQL + 同源 SPA 对这个数据量和业务复杂度是合适的；不需要微服务、Go 或 NoSQL。2 万份病历用关系库加索引是对的。 |
| 并发架构 | **是** | 写路径的长事务行锁、每请求审计写入、同步导出，把“并发”变成了“排队”。这些是为正确性做的设计，但吞吐上限是结构性的。 |
| 导出契约 | **是，且最硬** | 大导出 + 先审计后返回 + 完整响应计时三者同时成立，4,000 份规模下 280 ms 无解。 |
| 测量方法 | **部分是** | 同机压测把客户端开销混入服务端时延；先分离压测机，才能区分“真容量”与“测量污染”。 |

所以，**不是“单体架构选错了”**。真正的问题是：这个单体在正确性上做得比较重（行锁、同步审计、同步导出），而冻结负载把它推到了 1,286 次/秒的容量等级；这是并发架构与契约问题，不是“要不要拆微服务”的问题。

## 5. 达标路径

### Tier 0：先定口径（零代码，必须先做）

1. 和老师确认 360 是“并发用户”还是“持续在途”。
2. 确认大导出是否允许异步、单列 SLO 或设置单次范围上限。
3. 在确认前，不修改冻结协议、不降低门槛、不宣布 AC-06 通过。

### Tier 1：低成本、低风险（天级）

- 压测客户端迁到独立机器，服务端只跑 Waitress + MySQL。
- `CONN_MAX_AGE` 设为正数并启用健康检查，或引入连接池；消除每请求新建连接。
- 2—4 个工作进程 × 60—120 线程（Linux/gunicorn 更合适；Windows 可用多进程 + 统一入口），避免单进程 120 线程的 GIL 与队列瓶颈。
- 批量/合并审计写入，减少每请求的往返；去掉 `protected` 与 service 的重复 `require()`。
- 给导出设置单次范围上限；小导出走同步，大导出走异步。
- 补导出过滤所需的索引，确认 `count()` 与分页计划。

预期：查询与小导出可以进入 280 ms；写/护栏仍受门店行锁限制；大导出仍会超。**不要用 Tier 1 的结果宣称 AC-06 通过。**

### Tier 2：中等架构改造（周级）

- 缩短写临界区：读 `PolicyHead` 版本快照，不在整个规则评估期间持有 `FOR UPDATE`；提交时做乐观版本校验，或按门店分片/队列串行。`Account` 锁也不要覆盖整个事务。
- 大导出异步化：创建任务返回任务号，后台生成 CSV 并写对象存储；审计在文件可见前提交；客户端轮询/下载。若课程要求“导出接口 P95 含完整响应”，则必须把大导出单列 SLO，或经批准调整配比。
- 连接池/代理（如 ProxySQL）+ 多应用节点；把 500 级别的并发连接压到数据库能承受的范围。

做完后必须按原协议完整复测；如果导出仍按同步大导出统计，仍然过不了。

### Tier 3：换容量等级（月级）

多节点无状态应用层 + 负载均衡 + 更大 MySQL/读写分离 + Redis 会话/缓存。只有确认必须按 B 口径验收才值得；对课程项目通常不划算，也会显著增加权限、审计和一致性验证成本。

## 6. 对 AC-06 的结论与交付建议

- **A 口径：** 这个指标是合理且可达的。值得做 Tier 1 + 部分 Tier 2；如果老师同意按“360 个并发用户（有思考时间）”复测，应重新形成明确协议并记录，而不是在旧协议上事后改解释。
- **B 口径：** 当前单机同步架构达不到；病历导出类在现行契约下算术上不可能。Tier 1/2 有机会把 12—34 秒显著降下来，但**不能把导出类 P95 降到 280 ms**。AC-06 应继续保持“未通过”。
- **交付表述：** 如实写“功能闭环 + 容量分析 + 实测缺口”，不要把 27.2 次/秒或 800 次/分钟单独摘出来说“达标”。如果决定投入优化，按冻结协议原规模、原配比、完整响应计时复测；短探针或更强机器的结果单独标注环境，不能覆盖现有失败轮。
- **不建议：** 为了一个在 B 口径下需要 1,286 次/秒的数值，去重写已经验证过的权限、审计和事务路径；投入产出不成比例，且会引入新的正确性风险。
