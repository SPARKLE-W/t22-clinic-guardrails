# 严格 280 ms 工程改造评估

> 2026-10-28；评估对象为当前 `main` `17335e8`、已冻结的 [TBR-05 v1.0](01_正式负载测量协议_v1.0.md) 及[第二轮正式结果](05_正式负载第二轮实测.md)。本文回答“如果一定要在严格口径下达到 P95≤280 ms，应该怎么做”，是工程评估与试验计划，**不是 AC-06 通过记录**，不改代码、不改冻结协议、不降低门槛。此前对话中的“380 ms”是口误；任务书原文是 **280 ms**，本文不采用 380 ms 作为目标。

## 0. 结论摘要

1. **只调线程/加机器达不到。** 当前 120 个 Waitress 线程、同机压测、`CONN_MAX_AGE=0`、按门店串行的 `PolicyHead`/`Account` 长事务锁，以及 4,000 份导出的同步审计，共同把 360 持续在途下的 P95 推到 12—34 秒。
2. **严格 280 ms 是容量等级问题，不是单条 SQL 问题。** 按 360 在途、平均时延接近 280 ms 估算，稳态完成能力约 `360 / 0.28 ≈ 1,286 次/秒`；这是量级示意，不是由 P95 单独推出的硬性下界，但足以说明当前 27.2 次/秒差了一个数量级以上。
3. **必须按“测量归因 → 运行容量 → 锁临界区 → 导出契约 → 全协议复测”的顺序做。** 先证明瓶颈在哪，再改；不能凭代码直觉重写权限/审计路径。
4. **最硬的两处是写锁和 4,000 份同步导出。** 写锁把同店写请求串行；4,000 份导出的审计目标插入单项约 0.594 秒，已超过 280 ms。前者可通过版本快照/乐观校验改造；后者要么把单请求成本压到 280 ms 以下，要么改导出契约（异步/范围上限/配比），而改契约需要本人和老师批准。
5. **单机分层单体仍有争取空间，但不能承诺。** Linux 多进程 + 360—480 个处理槽 + 连接池 + 写锁重构 + 导出批量优化，是单机内最现实的组合；若 1,286 次/秒的混合写/导出/审计仍压垮单机 MySQL，严格 280 ms 就不能在题定“单机数据库”边界内闭合，只能如实报告未通过，或经批准调整契约。

## 1. 目标与口径

严格口径按 [TBR-05](01_正式负载测量协议_v1.0.md)：

- 360 个请求**持续在途**，无人工思考时间；
- 300 秒预热＋600 秒正式窗口；
- 查询 30%、护栏 15%、接诊 15%、写入 20%、三类导出合计 20%；
- 病历导出中 10% 为 1,000—4,000 份；
- 计时从发起到**完整响应体接收**，含授权、业务、必要审计、CSV 生成与传输；
- 七类 P95 均 ≤280 ms、正式窗口零业务失败、逐分钟 ≥800 次。

“活跃会话 360、思考 15—25 秒”是另一种口径，已有 [24 号结果](24_AC06课程口径v1.1完整验收.md)：360 个会话复用 19 个业务账号，10,774 次、0 失败、P95 65.1—138.4 ms、实际在途 P95=3/峰值 12。它证明低在途下应用可以很快，但**不能替代严格 360 在途**；本文只讨论后者。

## 2. 当前证据与差距

| 项 | 当前值 | 严格 280 ms 的含义 |
| --- | --- | --- |
| 吞吐 | 约 27.2 次/秒 | 按 360 在途、平均 280 ms 估算需约 1,286 次/秒；差约 47 倍量级 |
| 七类 P95 | 12.2—34.0 秒 | 需全部 ≤280 ms |
| 入口 | Waitress 120 线程；25,135 条队列告警，最大深度 242 | 360 在途时线程全忙，请求在入口排队 |
| 数据库连接 | MySQL `max_connections=151`；`CONN_MAX_AGE=0` | 每请求新建连接；360—480 个处理槽需要连接预算/池化 |
| 写路径 | `Account`、`PolicyHead`（每店一行）、`Encounter` 三处 `SELECT ... FOR UPDATE` | 同店写请求串行；锁覆盖规则评估与审计 |
| 导出 | 4,000 份约 3.09 MB/776 ms；单次 SQL 约 1.7 s；4,000 条审计目标插入约 0.594 s；生成在事务内 | 大导出单请求已超 280 ms；混合负载下还会放大 |
| 压测环境 | 客户端、Waitress、MySQL 同一台 Windows | 客户端 CPU 与服务端争抢，测量被污染 |

补充：`21_AC06原文口径与性能改进决策.md` 已指出，`360/0.28≈1,286` 是“平均时延接近 280 ms”时的容量示意，P95 不能单独推出硬性吞吐下界；120 线程也不自动等于“必须 360 线程”。本文沿用这一谨慎口径：**1,286 次/秒用于判断数量级，不作为数学证明；最终以分段实测为准。**

## 3. 先做归因：不要直接改架构

严格达标的第一步不是加线程，而是把 12—34 秒拆开：

| 区段 | 记录内容 | 目的 |
| --- | --- | --- |
| 客户端 | 发起、首字节、完整接收、重试/超时 | 排除客户端与同机争抢 |
| 入口 | Waitress 队列深度、活跃线程、入队到视图开始 | 判断是否入口排队 |
| 应用 | 视图开始/结束、授权、规则评估、序列化 | 区分业务逻辑与排队 |
| 数据库 | 每条 SQL 耗时、`Threads_running`、`Innodb_row_lock_time`、慢查询 | 判断 SQL/锁等待 |
| 审计 | `AuditEvent`/`AuditTarget` 插入与提交 | 判断审计成本 |
| 导出 | 预取、CSV 生成、SHA-256、审计、完整发送 | 定位大导出成本 |
| 资源 | CPU、内存、磁盘 IOPS、网络、连接数 | 判断是否硬件饱和 |

试验设计：

1. 压测客户端迁到独立机器；服务端用 Linux（Ubuntu 24.04）或至少与客户端分离。
2. 固定源码、夹具、种子、配比；先做 1/10/30/90/180/360 在途逐级短探针，每级 60 秒，保留原始请求。
3. 每级按七类分别统计 P50/P95/P99、失败、队列深度、SQL/锁等待、CPU/IO；不允许只报总 P95。
4. 通过门槛：能明确指出每一类的前两位成本；若低并发单请求已 >280 ms，先优化该请求；若低并发快、360 在途骤慢，先查入口/连接/锁。

## 4. 改造方案

### 4.1 运行容量：单机多进程 + 连接预算

- **Linux 多进程**：8 个进程 × 45—60 线程（gunicorn `gthread` 或等价），总处理槽 360—480；不要再靠单进程 120 线程硬撑。多进程仍是单机分层单体，不是服务拆分。这里的 360—480 是按 360 在途、留 20—30% 余量的工程配置，不是由 120 线程公式推出的唯一答案；实际线程/进程数由分段测量决定。
- **连接**：`CONN_MAX_AGE` 设正数并启用健康检查，或使用连接池/代理；MySQL `max_connections` 至少 500—800；每个进程的连接预算要核算，不能 480 个线程各自无限开连接。
- **系统**：文件描述符、TCP backlog、临时端口、TIME_WAIT 复用；服务端与压测机分离；关闭无关后台任务。
- **数据库**：16—32 核、64 GB、NVMe；`innodb_buffer_pool_size` 覆盖热数据；在保证审计持久性的前提下调优 `innodb_flush_log_at_trx_commit`、日志文件、IO 容量；监控 `Threads_running`、锁等待、慢查询。
- **验收门槛**：360 在途 60 秒短探针的入口队列深度显著下降；P95 从十秒级降到秒级；若加进程后数据库锁等待/CPU 反而上升，停止加线程，转入锁与 SQL 优化。

### 4.2 写路径：缩短 `PolicyHead`/`Account` 临界区

当前 `clinic/writes.py` 在事务开始就锁 `Account`、`PolicyHead`、`Encounter`，直到规则评估、插入、审计全部完成。`PolicyHead` 每店一行，等于同店写请求串行。

候选改法（按风险从低到高）：

1. **只锁目标接诊行**：`Encounter` 行锁保留，用于版本/状态冲突；`Account` 只做普通读取/权限校验，不用 `FOR UPDATE` 覆盖整个事务。
2. **策略版本快照 + 提交时校验**：读取当前 `PolicyHead.generation/candidate` 快照，不持锁；在提交前用条件更新或再次读取校验版本；版本变化则重试，保证“校验用的规则版本=提交时生效版本”。
3. **幂等键唯一约束**：用 `(actor, permission, key)` 唯一索引 + 冲突捕获，替代长时间锁 `Account`；重复请求返回原结果，不重复写审计。
4. **按门店分片/队列串行**：若测量证明同店策略版本冲突是主因，可把同店写请求放入有界队列，由单 worker 串行处理；仍是单机，但吞吐受队列服务率限制，需实测。

必须保留的正确性：规则版本与病历提交一致、撤权即时生效、审计与病历同事务、逐目标可追溯、重复提交幂等。每项改动都要有“策略在写入中途变更”“账号在写入中途撤权”“同键重试”“审计失败回滚”的负例。

**验收门槛**：写入/护栏类 P95 进入 280 ms 附近；`Innodb_row_lock_time` 占写延迟比例显著下降；并发回归通过。

### 4.3 导出：先把单请求成本打下来，再谈契约

4,000 份导出当前：完整 HTTP 约 776 ms，SQL 约 1.7 s，其中 4,000 条审计目标插入约 0.594 s。0.594 s 是**一次观测**，不是不可优化的数学下界；但它是当前最明确的单请求下界来源。

优化顺序：

1. **审计批量**：确认 `bulk_create` 的 batch size、索引数量、事务提交次数；减少 `AuditTarget` 不必要的二级索引；用多行插入/批量提交；测量 1,000/2,000/4,000 三档的实际插入时间。
2. **查询与生成**：按 SQL 计划优化预取；CSV 分块生成；SHA-256 只对最终字节算一次；避免重复模板解析。
3. **单请求目标**：4,000 份完整响应 ≤280 ms。如果优化后仍 >280 ms，记录各段成本，不要直接断言“绝不可能”。
4. **契约选项**（需本人/老师批准）：
   - 异步导出：请求返回任务号，后台生成到对象存储，客户端轮询/下载；审计在文件可见前提交。严格协议的“完整响应计时”需相应修改，否则不能算通过。
   - 单次范围上限：把 1,000—4,000 份移出同步 P95，或把大导出占比降到 5% 以下；这同样是改配比/协议。
   - 独立 SLO：导出按大小分层，大导出单列目标；不能把大导出从统计中静默删除。

**量级压力**：严格 1,286 次/秒下，20% 是导出；若三类导出各约三分之一、病历导出中 10% 为大导出，则大导出约 `1,286×20%÷3×10% ≈ 8.6 次/秒`；每次 4,000 个审计目标就是约 **3.4 万目标/秒**。若三类都按病历规模计，最高可到 10 万/秒。这个量级不是靠单机逐条插入能轻松承受的，必须以批量/异步/契约三者之一解决。

### 4.4 读取与序列化

查询本身不是最大头：早期分段中 app 内 P95 约 87—210 ms。严格达标仍需：

- 组合索引覆盖门店/医生/时间/状态；列表 keyset 分页，避免大偏移；
- 只取白名单字段，不预取无关历史；
- 缓存模板/策略版本，减少重复解析；
- 去掉 `protected` 与 service 的重复 `require()`；
- 读取审计保持同事务/成功后返回，不能为降时延删除。

### 4.5 压测与验收

- 独立压测机；固定源码、夹具、种子、配比；300 秒预热＋600 秒正式；
- 七类分别统计 P50/P95/P99、失败、每分钟完成数、实际在途、资源；
- 保留原始请求级数据、命令、环境、数据库/中间件版本；
- 只有七类 P95≤280 ms、0 失败、每分钟≥800、360 在途同时成立，才能写“严格口径通过”。

## 5. 分阶段执行与停走条件

| 阶段 | 工作 | 通过门槛 | 失败时 |
| --- | --- | --- | --- |
| 0 归因 | 独立压测机、Linux、分段计时、逐级短探针 | 能说出每类前两位成本 | 先修测量/单请求，不进入扩容 |
| 1 运行容量 | 8×45—60 线程、连接池、MySQL 500—800 连接、系统/DB 调优 | 360 在途队列显著下降；P95 进入秒级 | 若 DB 先饱和，转 4.2/4.3，不盲目加线程 |
| 2 写锁 | 只锁接诊行、策略版本快照、幂等唯一键 | 写入/护栏 P95 接近 280 ms；锁等待下降 | 若正确性负例失败，回退并保留原锁 |
| 3 导出 | 批量审计、SQL/CSV 优化；必要时谈异步/范围/配比 | 4,000 份单请求 ≤280 ms，或契约获批 | 未获批则严格导出类不能判通过 |
| 4 全协议 | 原 300+600 秒、原配比、完整响应 | 七类 P95≤280、0 失败、≥800/分钟 | 如实报告未通过，不挑样本 |

工作量级：阶段 0—1 天级，阶段 2—3 周级，阶段 4 天级；如果涉及导出契约变更，另加确认与回归时间。不要把“短探针变快”当成正式通过。

## 6. 可行性与边界

- **当前 120 线程 Windows 单机：不可达。** 不是再调一条 SQL 能解决；入口、锁、导出三处都需要改。
- **单机 Linux + 360—480 槽 + 连接池 + 写锁重构 + 导出优化：有可能，但不能承诺。** 1,286 次/秒的混合负载、每请求审计、4,000 份导出，对单机 MySQL 是极限测试；必须用分段数据决定是否继续。
- **4,000 份同步导出 + 10% 配比：最可能的硬阻塞。** 若优化后单请求仍 >280 ms，且老师不允许异步/改配比，则严格 AC-06 不能通过；这不是“云服务器不够”，而是契约与容量问题。
- **不要用活跃会话 65—138 ms 替代严格 360 在途。** 两种口径必须并列；严格未通过就写未通过。
- **不要为了时延删除审计、权限、版本校验，或把审计移到响应之后。** 这些是本题的安全底线；改契约必须本人/老师批准并重新验收。
- **380 ms 不是题定值。** 任务书是 280 ms；如果老师口头说 380，先书面确认，不能自行把目标改宽。

## 7. 最小可行改造清单

如果只做一轮最可能见效的改造，按这个顺序：

1. 压测客户端独立；服务端 Linux；8×45—60 线程；`CONN_MAX_AGE`/连接池；MySQL 500—800 连接、16—32 核/64 GB/NVMe。
2. `clinic/writes.py`：`Account` 不再长事务 `FOR UPDATE`；`PolicyHead` 改版本快照 + 提交校验；`Encounter` 只锁目标行；幂等键唯一约束。
3. `clinic/exports.py`：批量审计、减少索引/提交次数、CSV 分块、SHA 一次；测 1k/2k/4k 单请求。
4. 若 4k 仍 >280 ms：和老师确认异步导出/范围上限/配比调整；未确认则严格导出类按未通过。
5. 原协议 300+600 秒完整复测；保留全部原始请求。

## 9. 2026-11-02 最新实测复核

本节以[多轮诊断记录](30_严格280ms多轮诊断记录.md)和[执行计划](27_严格280ms多轮测试与改进执行计划.md)中较新的测量为准；本文前面的初版测量和结论保留作历史，不作为当前瓶颈排序依据。

- 第35轮在360个请求持续在途、63.24秒内启动10037个请求、零失败；吞吐约159次/秒，但七类完整响应P95为5.69—11.10秒，离280毫秒仍差很远。第36轮正式长测有98.07%连接重置，判为无效，不用其延迟分位作性能结果。
- 轮21后续MySQL观测的75个样本未见行锁等待，活动事务峰值73、活动连接峰值88；这不支持继续把`Account`/`PolicyHead`行锁列为当前首要瓶颈。早期的写锁分析仍保留作历史与正确性风险说明。
- 轮30的服务器资源观测窗约74秒，主机CPU P95/峰值100%，可用内存最低约25.3 GiB；Web和MySQL进程CPU增量合计497.35 CPU秒，折合观测窗平均6.72个逻辑核。按10040个请求相除约49.5 ms CPU/请求是聚合比值，不是请求级CPU剖面。**若**维持相同工作组成和CPU/请求成本，并把平均完成能力量级推到`360 / 0.28 ≈ 1286 次/秒`，算术上约需64个逻辑核总CPU；这是规模估算，混合比例、P95与平均时延关系、源码变化和数据库扩展都会改变结果，不能据此下单或承诺配置。
- 较新负载使用独立工作站客户端，通过SSH转发访问ECS；故“客户端、Waitress、MySQL同机造成压测争抢”已不适用于后续轮次。当前确认的是ECS内Web与MySQL共用8 vCPU且CPU饱和，不能把客户端争抢当成主要解释。
- `StoragePerformanceReachLimit / SysDiskIOPS`事件提示应核查系统盘IOPS，但缺少事件同窗的客户端时间线、云盘PL、Windows物理盘映射及实例级监控，尚不能断定磁盘是导致断连或高P95的主因。

### 当前架构结论

已有证据说明当前8 vCPU单机同时运行Web与MySQL时容量不足以通过严格负载；但没有证据证明Django/DRF必须整体重写、切换异步框架或微服务化。单纯加Waitress线程也没有稳定解决延迟。代码层减少查询/序列化和写放大仍值得在安全边界内继续；不过若保持当前约49.5 ms聚合CPU/请求量级，280 ms附近的360在途将要求远高于8核的CPU能力，单靠小幅代码微优化不足以闭环。

ECS恢复后，架构候选应以相同源码、夹具、负载种子和网络路径做可复现短轮A/B：①当前单机与提升CPU/系统盘性能的单机；②应用与数据库分离并为数据库配置独立CPU及高性能数据盘。分别记录应用/MySQL CPU、数据库提交与SQL分段、磁盘IOPS/延迟、队列和七类完整响应P95。只有结果重复改善后再选实例规模；在此之前不宣称需要固定的64核规格。必须保留现有同步授权、审计、数据范围和TBR-05口径；异步导出或放宽范围属于需求变更，不能作为隐式性能优化。
