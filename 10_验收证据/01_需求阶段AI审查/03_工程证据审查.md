## 2. 应尽早验证的五项工程风险

### E1 单机分层单体能否在完整安全路径下承载题定负载

**依据：** T§3第5项、§5第1—2项、§6、AC-06；C§4；P§5.3。

**风险：** 前后端分离与单体分层并不冲突。前端通过明确 API 访问同一后端应用；后端内部区分接口、业务、规则/权限和数据访问层。单机可以运行数据库、消息组件及必要任务执行进程；这不自动等于业务服务拆分。需要避免按“微服务+网关+集群”的方向扩张，也不能把一个只有后端脚本的演示称作交付完整。一个请求会经过身份、行级判定、规则校验、事务和审计，裸查询性能不能代表最终接口性能。

**候选与预研任务：** 在 architecture.md 中比较至少两套完整候选，例如“独立 HTML/JavaScript 界面 + Django + MySQL + RabbitMQ”和“独立 HTML/JavaScript 界面 + Flask + PostgreSQL + RabbitMQ”。这些仅为比较对象，不含版本选择或性能保证；也可由本人提出其它候选。分别比较开发成本、单机并发/事务风险、可维护性和 3200—4800 有效行预算。先画单机组件与层间调用图，再计划一个含授权、写入、审计、导出和待发记录的最小切片；通过实际预研比较锁等待、连接等待、审计开销和导出开销。

**通过判据：**

- 设计图显示前端、一个后端应用、单机关系库及至少一个常规中间件；业务不拆服务、不依赖集群或多地域。所有业务写入必须经过控制文件和统一权限入口。
- 预研在约定数据分布下覆盖真实安全路径，产出请求数、错误、分接口时延及数据库等待证据；若未满足候选门槛，保留失败结果并调整候选，不能先关闭审计再测。
- 正式验收另行执行：5店、约6000宠物、约2万病历，360并发持续10分钟；查询、校验、导出分别 P95≤280ms，正常授权负载无失败，混合吞吐≥800次/分钟。该目标目前没有达标结论。

### E2 权限、业务事务与审计能否形成没有旁路的闭环

**依据：** T§4 FR-04—FR-06、FR-08，§5第3—4项，§6锁定约束，AC-03、AC-04、AC-07；C§3.1；P§5.1—§5.2。

**风险：** 登录成功不能代替行级授权。详情、列表、搜索、导出、统计和审计查询都可能绕过同一权限策略。管理者统计权限不能自动扩张成病历全文权限。病历写入和访问审计若分两次提交，可能形成“业务成功、审计缺失”；反过来，把拒绝事件放入被回滚的业务事务又会丢失拒绝证据。

**候选与预研任务：** 先起草角色×动作×字段×门店×归属矩阵，以可信身份与服务端归属计算范围，客户端提交的角色/门店/医生编号不能自行授权。提出“服务端统一授权入口 + 受范围约束的数据访问 + 默认拒绝的路由登记门禁”方案。设计三条时序：允许读取并成功落审计后返回、业务与审计同一事务提交、拒绝/失败事件在业务回滚后仍持久留存。拒绝日志不得带病历全文或原始口令。

**通过判据：**

- 按本人确认的矩阵，分别通过页面和直接 API 验证同店本人允许、同店非本人拒绝、跨店拒绝、前台/管理读取全文拒绝；列表和导出只能返回获准范围，统计与审计查询不泄露全文。
- 每次允许读取与导出都有可按病历和操作者检索的审计；导出含导出人、范围和用途。写入故障注入后，病历与该次业务审计只能同时提交或同时回滚。
- 拒绝事件含请求者、目标记录与原因；业务回滚、授权失败后仍可查拒绝证据。审计不可用时，不返回未经审计的病历数据；具体失败响应作为待审接口方案。
- 人为放入未登记授权的测试端点，扫描应失败并阻断发布，实际调用也应拒绝并记录。公开认证等端点明确登记，不能靠“所有接口需要先登录”形成循环。
- 连续与并发重复提交不产生重复业务；处方、用药与剂量更正保留原记录；幂等键复用但请求内容改变时的响应有明确设计和测试。

其中“转诊/接班后的归属变化、接诊信息字段、审批与审计查看职责”必须由本人确认后才可定稿；本轮可先列候选和待审单元格，不需等全部确认才能画时序或写负向用例。

### E3 控制文件是否真正控制生成、生效和历史解释

**依据：** T§3第1项、FR-01、FR-02、§6锁定约束、AC-01、AC-02、§12第4项；C§3；P批次A。

**风险：** 静态 JSON/YAML 文档不等于“由需求生成、缺项或冲突生成失败”。生成失败却残留可被运行时加载的半成品，或者运行时对缺键静默使用代码默认值，会绕过红线。只保存模板版本号而覆盖旧版内容，也无法证明旧病历仍按原版解释。

**候选与预研任务：** 起草控制文件模式、需求→规则映射、人工评审→生效流程；区分“生成候选”“通过结构/红线校验”“人工评审生效”。提出先校验候选、成功后再发布版本，失败不替换已生效版本的方案。对安全红线、编码规范、质量门禁以及权限/字段引用分别准备缺项、冲突和无效引用样本。模板定义与病历使用的版本绑定，旧版定义保留。

**通过判据：**

- 合法输入产生可追踪候选；缺项、红线冲突、无效引用均明确失败，给出错误位置/原因，不产生被系统视为有效的新版本，不回落到隐藏默认值。
- 未经本人确认评审的候选不能生效；变更保留来源、真实评审人、生效时间和版本。该流程可以先以文档/控制文件方式设计，不擅自增加第四种系统角色。
- 提交更高版本模板后，同一旧病历仍按原版字段和含义解释；新病历引用新版本。直接绕过控制文件尝试写病历应失败。
- 各设计一次新增规则、新增模板的演练，记录实际变更和投入；正式维护性验收需证明每次≤1个规则文件+1个模块、人日≤1，不以估计替代事实。

### E4 常规中间件、消息补发与定时重入不能混为一项

**依据：** T§5第3项、§6交付范围、§9中间件专项、FR-07；C§1.1第3项、§4.1；P批次D、§5.2。

**风险：** “至少一个常规中间件（消息队列、定时调度器）”没有取消“消息队列不可用时本地待发、恢复补发”的明确要求。因此仅选定时器、内存列表或把本地数据库表命名为队列，不能据此认定可靠性验收已满足。另一方面，工具表提到定时任务重入，并不足以自动推出必须再装一个独立调度平台。

**候选与预研任务：** 比较 RabbitMQ 等常规队列候选；提出“告警/本地待发持久化 + 队列投递 + 幂等消费”的方案。待发状态与相关业务/告警落库的原子边界须画清；投递后、标记成功前崩溃会导致重复发送，消费端必须能识别同一事件。补发触发可比较应用任务循环与常规定时调度器，不因工具名增设系统。此处讨论的是应用任务职责，不能扩成业务微服务。

**通过判据：**

- 后续真实停用所选队列时，护栏命中仍留下完整告警及持久待发项；重启应用后待发项仍在，未处理告警持续提示。
- 恢复队列并完成补发后，对照事件编号核对：应发集合全部到达、没有永久丢失；重复投递可发生，但每个事件不形成重复业务处理。记录积压数量、恢复时间线、投递/消费结果。
- 故障点至少覆盖投递前、发送成功但尚未标记、重复消费和补发执行中重启；重试有明确失败状态，不能无限失败仍展示“已发送”。
- 如果采用定时补发，同一批任务重入/重叠时仍不重复处理；若未采用定时器，先提交适用性说明和实际补发机制证据，不自行宣布免检，也不把整张工具表扩大成必装组件清单。

恢复后补发的最大等待时间未被任务书量化，可先提出可配置演示窗口及可观察状态供本人审查；不用把具体秒数变成必须问老师才能开工的问题。

### E5 压测、覆盖率与代码规模能否形成可复核的测量口径

**依据：** T§5、§6、AC-06、AC-08、§9；S§2.1、§八、附录B；C§4、§4.1、Q08；P§5.3、§8。

**风险：** 360个登录账户、360个虚拟用户和360个同时在途请求不是相同口径；设置大量思考时间后仅追求800次/分钟，也不能据此证明承载360同时请求。合并P95会掩盖慢导出。异步导出仅返回任务号的时延不能冒充导出完成时延。80%若只统计少量易测模块，或有效行数混入生成代码/空行，都缺乏可复核性。

**候选与预研任务：** 先写压测协议草案，不立即运行。记录环境、固定数据生成种子/分布、接口组合、导出范围与字节数、认证方式、请求计时边界、预热和正式600秒窗口。明确负载模型，保留目标并发、实际活跃用户和实际在途数；在老师未进一步解释之前，可先提出360持续活跃客户端且不靠人为长等待压低负载的保守方案，同时报告实际并发。导出选择有代表性范围并说明场景；不能擅自把导出限制成空结果来满足时延。

**通过判据：**

- 正式协议能重建同一数据和正常授权流，360并发、600秒、P95≤280ms、无失败与≥800次/分钟在同一正式窗口核对。按查询、校验、导出分别报告样本量与P95，接诊/写入/导出均进入负载；原始数据包含超时和错误，不只保留成功请求。
- 若“≥800次/分钟”暂按正式窗口平均统计，同时列出逐分钟数据；不以平均值掩盖中途停顿。若后续验收要求逐分钟达标，按明确口径执行。预期安全拒绝单独测试，不能拿其替代授权成功吞吐。
- 导出计时包含已声明的完整处理与响应边界；若异步，任务接受与任务完成两套时延分别呈现，未澄清前不能用接受时延代替T§5的导出指标。
- 覆盖率报告列明源码范围、统计类型与排除项；正式全量用例通过且覆盖率≥80%。所有安全核心模块与故障路径有断言，不能仅以总覆盖率代替越权/事务正确性。
- 有效代码规模3200—4800行有可复现计数脚本/命令及排除清单；分别展示应用、测试、配置等类别，待确认口径下不灌水、不把第三方/生成文件算成本人有效实现。
- 第9节十类检测逐类有适用性、拟用工具和对应证据；先按任务书列出的工具形成方案。只有发生工具不适配或拟替代时才集中澄清等效口径，不把每个名字变成独立阻塞问题。

## 4. 对现有流程的最小调整建议

1. 在 P 阶段1—2并行形成五项风险的设计检查表和测试输入，不等整套设计完成才发现测量定义与事务边界缺失。先完成可审查提案，再请求本人确认真正的人类决策。
2. 技术选择前比较至少两套候选；本人确认后，只针对允许候选做最小预研。优先顺序为权限/事务切片→控制文件拒绝闭环→队列故障恢复→带完整安全路径的负载预研。
3. 将E5测量协议、行数预算和覆盖率范围提前确定为证据模板；正式压测仍在功能、权限、审计和导出完整后执行。预研值不得写入AC正式通过栏。
4. 每项后续结果记录“需求来源→提案/人工决定→实现版本→测试命令→原始证据→结果/限制”。失败和未验证状态必须保留；AI复核意见也需经证据核对，不以多名AI意见一致代替验收。

## 6. v0.2定点复核与下一轮三项优先预研

> 复核日期：2026-10-19。输入为冻结的 [需规v0.2复核快照](D:/大三/课程/软件设计与开发/大作业/10_验收证据/01_需求阶段AI审查/04_需规v0.2_复核快照.md) 与 [需求阶段协作记录](D:/大三/课程/软件设计与开发/大作业/07_AI使用留痕/01_需求阶段协作记录.md)。前述初审及v0.1补审意见保留为当时状态；本节不反写其结论。此次仅做文档复核及预研排序，未联网、安装、实施或测试。

1. **原DEC-02文档风险已收口。** 快照§3.1、DEC-02与协作记录§1的实际问答一致：按次隔离、建档成功即固定门店/前台/医生归属，首版无转诊、换班或跨店调阅；“宠物完整历史可见”备选已移除。DEC-03也以本人实际回答限定管理本店汇总、脱敏审计和规则模板审批，医生处理本人告警。自由选型已确认，但不等于具体栈已获批准。此处关闭的是原备选表述风险，未来实现是否正确仍待E2验证。

2. **E2—E4仍是后续设计和验证输入。** 协作记录R-07正确保留读审计失败不返回病历、拒绝日志不随业务回滚、生成失败不换有效版本及投递后未标记的幂等恢复，没有宣称已实现/已通过。具体脱敏字段、审批生效及提交职责仍属后续提案；本人课程评审与系统管理账号审批必须继续分开。v0.2 NFR-02补入接诊/写入P95、NFR-08补入接口错误码对账，后续测量应沿用该补全，不只照初审中查询/校验/导出的简写执行。

3. **优先预研一：权限、读写审计与失败事务（E2）。** 下一轮先提交完整权限矩阵和允许读取、业务写入、拒绝留痕三条时序，再对本人允许的技术候选计划最小切片。预期出口：同店非本人/跨店/全文越权和建档后改派均被拒且有记录；允许读取先落审计再返回；故障下注入病历与业务审计同时提交或回滚，拒绝记录仍留存；管理审计不含被禁止临床内容。检查对象包括直接API、列表、导出、审计查询，不能只看页面。此阶段先设计输入和断言，未经后续实施授权不运行。

4. **优先预研二：规则候选、审批生效和版本解释（E3）。** 下一轮提交控制文件模式、生成/校验/审批/生效状态及历史模板绑定方案；审批角色遵循DEC-03，具体生效细则继续标提案。预期出口：合法、缺项、红线冲突和无效引用输入有可复核预期；失败不替换当前有效版本、不静默回落；未审批不能生效，旧病历仍按旧版解释。演示管理账号操作与本人真实设计判断分别留痕，不用模拟审批充当真人认可。

5. **优先预研三：队列故障、待发持久性及重复恢复（E4）。** 下一轮先提交队列候选比较、业务/告警/待发原子边界、补发与消费状态图，以及停队列/恢复/重启故障表。预期出口：停用队列仍持久保存告警与待发；恢复后应发事件集合全部到达；发送成功未标记和重复消费不形成重复业务；若采用定时补发，重入仍幂等。常规中间件方案与运行组件待审后再实施，不以数据库待发表或定时器名称自行豁免队列条款。这三项预研为带完整安全路径的性能预研提供前置切片，不代表360并发或正式验收已达标。
