## 1. v0.1到v0.2的显式技术映射

- 10个checker与failure_class字符串保持v0.1机械约束。按主代理本轮技术裁定：SR04新增`decision_change`；SR09新增`reception_change`、`decision_change`。前者承接既定不采纳留存，后者承接既定接待/不采纳幂等；不把这些操作命名为clinical_change。
- 旧输入/候选原样保留。新FloorSpec和新机器输入必须显式含新增phases；编译器不得给缺失的旧输入偷偷补齐后称通过。不改SRS或新增业务C项。
- `clinical_change`仅正式诊疗、更正、用药追加/更正和采纳；不采纳理由可空、不会写正式病历，也不会仅因拒绝就生成临床命中告警。前台接待阶段不获得临床权限。

- 同键摘要冲突、未胜出竞争或执行中不能进入新业务；所有回放仍当前授权，正式病历重读审计由SR06承接。

## 3. 事实严格类型及可信提供者

事实是登记的平面名字，点号不允许任意对象遍历。`boolean/integer/string/array`不做自动转换；integer拒绝bool、浮点和数字字符串；本提案数组仅string数组。枚举严格匹配，未知/错阶段/错类型在编译时失败；运行必需事实缺失按上下文/设施故障拒绝，不自动当临床命中。事实提供者名称是接入职责标识，不是已存在可调用模块。

| 提供者 | 信任与计算边界 |
| --- | --- |
| `compiler_floor_comparator` | 从严格解析后的定义与独立只读FloorSpec逐项计算；不读取输入自报的通过布尔值。 |
| `compiler_structure_validator` | 从实际JSON结构、引用图和三必需部分计算；缺项不得由隐藏默认值补齐。 |
| `authorization_entry` | 当前已验证会话及受保护操作登记；按服务端目标关联、行谓词和字段投影判定，不先加载无权正文。 |
| `policy_template_service` | 应用服务在同一操作边界固定的生效策略和记录原模板/实际目标版本；历史模板不替代当前授权。 |
| `clinical_change_service` | 医生服务依据当前目标、允许的写投影及拟持久化差异构造；不采信请求自报已通过。 |
| `suggestion_decision_service` | 已保存建议与接诊的真实关联、服务器当前状态和真实医生决定；不把客户端传入的来源当已保存来源。 |
| `governance_activation_service` | 同店管理服务核真实批准/手动启用步骤、版本内容摘要及当前生效指针。 |
| `audit_export_service` | 授权后构造必需留痕计划和完整文件释放门；写前只能描述设施及计划，不能证实未来commit。 |
| `release_gate` | 构建/发布阶段的实际路由登记及安全检查报告；静态报告不证明运行权限已实现。 |
| `persistence_adapter` | 实际参数绑定/口令表示及日志脱敏边界，不从普通主诉含引号推断SQL注入。 |
| `operation_recovery_service` | 服务端规范mode/target/业务输入/期望版本摘要、数据库OperationResult竞争及本地恢复设施。 |
| `outbox_receipt_service` | 服务端Outbox/租约/事件关联/消费者收据的真实状态；消息自报成功不构成持久事实。 |
| `commit_result_observer` | 提交返回及必要核对后的可确认持久结果；超时/断连保留unknown，不把未确认说成回滚或成功。 |

## 4. 写前与事后，尤其SR06

`audit.facility_ready`、`audit.required_plan_complete`和`audit.same_transaction_planned`只证明本次设施/计划前提。提案没有写前`audit_persisted=true`事实。`outcome.*`全部标为after_commit_only且condition_selectable=false，禁止拿来做写前附加条件；它们是未来应用服务提交观察者的结果契约，不是增加新phase。

- SR06读取：必需读取审计实际durable后才释放获准字节；旧结果重读仍有本次审计。正式写：业务/责任或采纳登记/必需审计同事务可确认committed后才报成功。
- SR06导出：完整CSV产物complete、本次必需审计durable及可确认提交结果先于字节返回；另记录真实行数/记录数。服务端就绪与客户端完整接收不同，物理磁盘保存不算后端完成。仅病历导出题定用途必填，不对命中导出新增必填用途。
- commit/audit为unknown时按需规核对，不伪报成功或回滚。SR09临床拒绝保留告警/拒绝/本地待发；broker不可用但本地持久成功走恢复，不等于留痕失败。消费者副作用与收据提交后才ACK；confirm/ACK均不等于医生处理。
- SR04不采纳实际保留来源及决定、formal_clinical_mutation=false；不要求采纳理由。SR05启用按真实批准内容和手动步骤核对，失败保留旧指针，未增加双人审批。
- after_commit_obligations的固定操作/可信分支和结果表达式在JSON逐项列出；本提案未执行这些义务，也不能把登记齐全称为数据库事务已实现。

## 5. 受限条件与不可绕过底线

附加条件仅present/eq/in/all/any；未知键、空args、空in值集、混合类型、未知事实/phase或循环引用均拒绝。eq/in仅标量严格同型，in是单个事实标量属于字面量列表，不隐式对运行数组做any。present不做truthiness：false和整数0仍是有效存在；null/错类型不算有效事实。

底线按固定operation/phase无条件调度，候选不得用when/条件包裹SR检查器、删phase、改checker或弱化failure_class。附加规则只能引用登记checker及其允许phase/typed facts，不能创建任意handler。候选编译失败只有校验报告/治理结果，不产生临床告警；`guard_hit_when_evaluated`字符串也不能单独当已发生命中。只有实际启用临床护栏被求值并命中才进临床告警路径。

## 6. 本提案实际检查与后续接入

本次只对两份登记提案做JSON语法、10项checker唯一性、旧checker/failure_class常量保持、phase/operation/fact引用及事后受限表达式类型的静态自检，未运行产品规则或服务。父代理纳入catalog时还应逐项核对：候选事实由独立机械比较得出而非输入自报；运行事实只能由登记可信服务提供；事后事实不能在写前条件使用；新增phase必须显式出现在v0.2输入/FloorSpec；不采纳/前台错误不生成临床告警。

当前10个运行handler、数据库提交观察/释放门、发布扫描器和实际Outbox接入仍属后续实现。运行时序与已完成操作回放必须遵守既定当前授权/不重做业务规则；此登记不替代这些接入或证明其已经测试通过。
